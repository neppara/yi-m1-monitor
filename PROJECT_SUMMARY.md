# YI M1 Camera Control — реверс-инжиниринг протокола и два приложения дистанционного управления

Сводка проекта для портфолио/резюме. Документ описывает, что было сделано, какие цели
достигнуты, какие — закрыты с отрицательным результатом (и почему это тоже результат),
и какие инженерные приёмы применялись.

---

## 1. Краткое описание (elevator pitch)

Полностью реверс-инжинирены закрытые протоколы управления беззеркальной камерой
**Xiaomi YI M1** (BLE-пейринг + HTTP/UDP по Wi-Fi), на их основе с нуля написаны **два
самостоятельных приложения** — десктопное для macOS (Python/PySide6) и мобильное для iOS
(Swift/SwiftUI). Оба превращают телефон/ноутбук в полевой монитор камеры: живое видео,
удалённая съёмка, управление настройками, файловый менеджер, вспомогательные инструменты
оператора (focus peaking, композиционные сетки, индикация границ кадра).

Отдельно проведено исследование осуществимости RAW-видео (в духе Magic Lantern) —
закрыто аргументированным «невозможно» с доказательной базой.

**Ключевая особенность проекта:** никакой официальной документации протокола не
существует; всё поведение камеры установлено экспериментально — дизассемблированием
прошивки, декомпиляцией официального Android-приложения и живыми тестами на железе.

## 3. Что было реверс-инжинировано

Протокол не документирован. Восстановлены и подтверждены живыми тестами:

### 3.1. BLE-пейринг (последовательность рукопожатия)
- Сканирование → выбор устройства по рекламируемому UUID сервиса → подключение →
  обнаружение характеристик.
- Обмен: чтение firmware-информации, генерация случайного ключа, запрос сопряжения,
  ожидание токена подтверждения с камеры (пользователь жмёт Accept на экране камеры),
  вычисление контрольной суммы **CRC32** от конкатенации ключа и токена, старт сессии.
- Финальный шаг: чтение Wi-Fi-учётных данных (SSID + пароль, **генерируются заново каждую
  сессию**) и включение точки доступа камеры.

### 3.2. HTTP-протокол управления
- Команды передаются как JSON в query-параметре; ~40 команд классифицированы на рабочие,
  «мёртвые» и опасные.
- Реализовано: старт/стоп сессии дистанционного управления, спуск затвора, запись видео,
  13 групп настроек (ISO, выдержка, диафрагма, экспокоррекция, баланс белого, режим
  экспозиции, замер, фокус, цветовой профиль, качество, пропорции, формат файла, режим
  протяжки), листинг файлов, скачивание, удаление.

### 3.3. UDP-поток живого видео
- Формат кадра восстановлен по байтам: заголовок пакета (индекс кадра, общее число пакетов,
  индекс пакета) + фрагмент полезной нагрузки.
- Обнаружено, что **первые 2048 байт собранного кадра — это JSON с актуальным состоянием
  камеры** (ISO, выдержка, баланс белого, видеоформат и т.д.). Раньше эти байты просто
  отбрасывались; их разбор позволил синхронизировать интерфейс с реальным состоянием
  камеры, а не только с тем, что приложение само отправило.

## 4. Ключевые находки о поведении камеры (добыты экспериментально)

Эти факты нигде не документированы и получены только через живые тесты. Каждый из них
напрямую повлиял на архитектуру приложений:

1. **Ошибки приходят с HTTP 200.** Камера сообщает о сбое команды кодом в теле JSON
   (`{"code":1515}`), а не HTTP-статусом. Проверка только транспортного статуса приводила к
   рассинхронизации: приложение считало запись остановленной, тогда как камера продолжала
   писать.
2. **Камера обслуживает ровно одного клиента и один запрос за раз.** Параллельные HTTP-запросы
   отклоняются с ошибкой «rc only one».
3. **Во время записи камера намеренно душит поток живого видео до ~7.5 fps** (вместо 30),
   отдавая ресурсы кодировщику. Это дало «сигнатуру», по которой можно программно определить,
   что запись завершилась.
4. **Лимит записи — по размеру файла, а не по времени:** 4 ГБ (ограничение FAT32). Для 4K это
   ~7 минут 29 секунд; бесшовной склейки файлов камера не делает — она жёстко останавливается.
5. **Видеоформат невозможно сменить дистанционно ничем** — команда присутствует в прошивке
   с валидным обработчиком, но HTTP-сервер отвечает 404. Плюс экран камеры блокируется на
   время Wi-Fi-сессии. Вывод: режим нужно выставлять на камере до подключения.
6. **Настройки едины для фото и видео** (проверено записью ролика с принудительным ч/б
   профилем — видео получилось чёрно-белым).
7. **Реальные области кадрирования измерены эмпирически** (штатив + эталонный снимок +
   шаблонный матчинг OpenCV, достоверность >0.95): 2K пишет полный кадр 4:3 без кропа,
   FHD — тот же кроп, что и фото 16:9, 4K — реальный кроп ~74%×56% с почти попиксельным
   считыванием сенсора.
8. **Часть полей метаданных «врёт»**: поле пропорций кадра всегда возвращает 4:3 независимо
   от выбранного значения, хотя сама команда установки работает корректно.

## 5. Приложения

### 5.1. macOS: «YI M1 Monitor» (Python + PySide6, ~3 900 строк)

Полноценное десктопное приложение в стиле нативного камерного интерфейса.

**Функциональность:** подключение по BLE или напрямую по Wi-Fi, живое видео, фото/видео
режимы, спуск затвора и запись, панель из 13 настроек, файловый менеджер (миниатюры,
множественный выбор, пакетное скачивание/удаление, предпросмотр), focus peaking,
композиционные сетки (трети, диагонали), рамка реальной области кадра с затемнением
обрезаемой части, поворот изображения для вертикальной съёмки, таймер записи,
автоперезапуск записи, восстановление Wi-Fi-сети при отключении.

**Архитектурное решение:** весь ввод-вывод (BLE, HTTP, UDP) изолирован в одном фоновом
потоке с очередью запросов; интерфейс общается с ним только через сигналы Qt. Это
структурно исключает конкурентные обращения к камере — то самое ограничение «один запрос
за раз», на котором спотыкалась первая версия iOS-приложения.

**Дистрибуция:** собрано в самодостаточный `.app`-бандл через PyInstaller (99 МБ),
запускается двойным кликом.

### 5.2. iOS: «YI M1 Monitor» (Swift + SwiftUI, ~6 200 строк, 38 модульных тестов)

Мобильный полевой монитор — телефон крепится на камеру и заменяет внешний монитор.

**Архитектура:** протокольный слой вынесен в отдельный Swift-пакет `YiM1Core` (не зависит
от UI, покрыт тестами), интерфейс — SwiftUI поверх протокола `CameraSessionProtocol`, что
позволяет запускать всё приложение на mock-реализации без камеры.

**Функциональность:** всё то же, что на macOS, плюс специфичное для мобильного сценария:
- **Ландшафтная раскладка полевого монитора** — изображение во весь экран, управление
  вынесено в боковые колонки вне картинки.
- **Быстрый выбор настроек в два касания** — тап по чипу раскрывает горизонтальный ряд
  значений с автопрокруткой к текущему.
- Запрет засыпания экрана, тактильная отдача, предупреждение о разряде батареи камеры,
  индикатор нестабильного радиоканала, сохранение файлов в системную галерею.

## 6. Инженерно сложные задачи (разобранные до корня)

Эти пункты показательны с точки зрения методологии — каждая проблема доводилась до
подтверждённой первопричины, а не «лечилась» симптоматически.

### 6.1. Расследование нестабильности видеопотока (многодневное)
**Симптом:** живое видео дёргалось, fps падал с 30 до 1–7, кадры пропадали.

**Метод:** вместо угадывания в приложение поэтапно встраивалась измерительная телеметрия:
раздельные счётчики сетевых потерь и потерь на стороне приложения; счётчик реального темпа
отправки камерой; статистика «сколько пакетов не хватило» у потерянных кадров; прямой
детектор «радио отсутствовало» по межпакетным паузам.

**Найдено и исправлено четыре независимые причины:**
1. Сборка кадра требовала строгого **порядка** пакетов — простая перестановка (не потеря!)
   уничтожала кадр. Переписано на сборку по индексам с окном на два кадра, что позволяет
   опоздавшему пакету достроить предыдущий кадр.
2. Декодирование JPEG выполнялось на главном потоке, что провоцировало отбрасывание
   свежих кадров политикой буферизации.
3. Недостаточный размер приёмного буфера сокета.
4. **Главная причина, установленная методом исключения:** аппаратное сосуществование
   Bluetooth и Wi-Fi на общей антенне iPhone. Последовательно исключены сотовые данные,
   AirDrop/Handoff, автоподключение к сетям; финальный тест с полностью выключенным
   Bluetooth дал стабильные 27–29 fps.

**Результат:** стабильные ~28 fps вместо 3–7; остаточные кратковременные просадки
идентифицированы как фоновое сканирование Wi-Fi самой iOS (неустранимо средствами
приложения) и задокументированы как ожидаемое поведение.

### 6.2. Почти непрерывная запись
**Задача:** камера жёстко останавливает запись на 4 ГБ (~7.5 мин в 4K).

**Решение:** упреждающий перезапуск записи по таймеру чуть раньше лимита + **страховочный
детектор** — приложение распознаёт самостоятельную остановку камеры по скачку темпа
живого видео (с ~7.5 к 30 fps) и мгновенно начинает следующий клип. Детектор
самокалибрующийся: взводится только после того, как убедился, что данный формат
действительно душит поток.

**Проверено в поле:** непрерывная 4K-съёмка с автоматической нарезкой на клипы по ~7 минут.

### 6.3. Расследование ограничений платформы (отрицательные результаты)
- **Автоподключение к Wi-Fi камеры на iOS** — реализовано, но выяснено, что необходимая
  возможность требует платного аккаунта разработчика. Код полностью откачен, реализован
  корректный запасной путь через ручное подключение.
- **Работа при заблокированном экране** — доказано, что iOS выгружает приложение; для
  сценариев длительной съёмки экран должен оставаться включённым.
- **Сборка macOS-приложения** — две первые попытки провалились из-за системы разрешений
  macOS: приложение должно быть тем процессом, которому система выдаёт права. Разобрано до
  сути и решено встраиванием собственного интерпретатора.
- **Bluetooth не подключался в собранном приложении** — оказалось, библиотека ждёт
  готовности стека ровно одну секунду и падает с ошибкой «Bluetooth выключен», хотя адаптер
  включён; при холодном старте стек не успевает подняться. Добавлены повторные попытки.

## 7. Исследование RAW-видео: закрыто с доказательствами

Исходная цель — выяснить, возможен ли Magic-Lantern-подобный хак для записи RAW-видео,
**строго программными средствами** (без пайки, UART, JTAG).

**Ответ: невозможно.** Каждая ветка закрыта отдельным доказательством:

1. **USB жёстко реализован как Mass Storage**, не PTP/MTP — путь эксплуатации через USB,
   работающий на Canon/Fujifilm, отсутствует.
2. **Требуемая пропускная способность физически недостижима:** по реальному DNG-файлу
   вычислено ~700–870 МБ/с для полнокадрового RAW-видео — недостижимо ни для одной SD-карты.
3. **Декомпилировано официальное Android-приложение** — в нём нет ни одной команды
   управления видеопараметрами. Команды существуют в прошивке с валидными обработчиками
   (подтверждено дизассемблированием), но не имеют ни одного клиента.
4. **Дизассемблированием подтверждено отсутствие скрытого маршрутизатора команд** —
   полная трассировка таблицы диспетчеризации.
5. **Инструмент перепаковки прошивки не даёт байт-идентичного результата** — прошивка любой
   модификации небезопасна.

Дополнительно исследованы и закрыты: чистый HDMI-выход (только воспроизведение; подключение
кабеля останавливает запись), обход лимита 4 ГБ через exFAT (камера требует FAT32).

**Ценность результата:** сэкономлены месяцы работы над заведомо тупиковым направлением;
вместо этого усилия перенаправлены на достижимые цели (два рабочих приложения).

## 8. Методология и инженерная культура

- **Ни одного «исправления вслепую».** Каждая гипотеза проверялась измерением или
  экспериментом; в проекте есть отдельные probe-скрипты для проверки конкретных гипотез
  (варианты параметров команд, влияние настроек на видео, реакция на разную длину запроса).
- **Все находки задокументированы с указанием причины.** Ведётся журнал багов «не наступай
  на те же грабли» с описанием симптома, корневой причины и решения — включая случаи, когда
  первое объяснение оказалось неверным и было опровергнуто.
- **Отрицательные результаты фиксируются наравне с положительными**, чтобы закрытые ветки
  не переоткрывались.
- **Тестирование без железа:** протокольный слой iOS покрыт 38 модульными тестами, включая
  воспроизведение сетевых сценариев (перестановка пакетов, потери, опоздавшие пакеты) на
  реальном UDP-сокете; для интерфейса сделана mock-реализация камеры.
- **Итоговый аудит обеих кодовых баз** свежим взглядом — найдены и исправлены гонка в
  детекторе остановки записи и блокирующая интерфейс операция загрузки миниатюр.

## 10. Формулировки для резюме

**Краткий вариант (одна строка):**
> Реверс-инжиниринг недокументированного протокола управления беззеркальной камерой
> (BLE + HTTP + UDP) и разработка двух кроссплатформенных приложений (iOS/Swift и
> macOS/Python) для дистанционной съёмки и полевого мониторинга.

**Развёрнутый вариант (маркеры):**
- Восстановил закрытый протокол управления камерой без документации: BLE-рукопожатие с
  криптографическим подтверждением, HTTP-команды, бинарный формат UDP-потока видео —
  через дизассемблирование прошивки (Ghidra), декомпиляцию официального приложения (jadx)
  и живые эксперименты на железе.
- Разработал два самостоятельных приложения: iOS (Swift/SwiftUI, Swift Concurrency,
  архитектура с изолированным протокольным слоем и 38 модульными тестами) и macOS
  (Python/PySide6, однопоточная модель ввода-вывода, сборка в `.app` через PyInstaller).
- Диагностировал и устранил комплексную проблему производительности сетевого видеопотока:
  внедрил измерительную телеметрию, нашёл четыре независимые причины (включая аппаратное
  сосуществование Bluetooth/Wi-Fi, доказанное методом исключения), поднял стабильность
  потока с 3–7 до 28 fps.
- Обошёл аппаратное ограничение записи (4 ГБ / ~7.5 мин) двухуровневым механизмом
  автоматического перезапуска: упреждающий таймер плюс детектор, распознающий остановку
  камеры по изменению характеристик видеопотока.
- Провёл исследование осуществимости записи RAW-видео и аргументированно закрыл его,
  доказав невозможность программными средствами (расчёт требуемой пропускной способности,
  анализ прошивки, декомпиляция официального клиента) — сэкономив месяцы работы над
  тупиковым направлением.
