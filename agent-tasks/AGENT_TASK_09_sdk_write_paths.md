## 3. ЗАДАЧА

Для **каждого из 10 режимов** проследить, что происходит при установленном флаге, и
дать ответ: **достигает ли исполнение функции ЗАПИСИ (флеш / EEPROM / калибровка), или
всё остаётся изменением поведения в RAM.**

### Стандарт доказательства — читай внимательно

Вывод по режиму принимается **только** в одной из трёх форм:

- **`ЗАПИСЬ НЕ ОБНАРУЖЕНА`** — ты проследил ВСЕ ветки от флага до терминальных точек
  (возврат из функции / бесконечный цикл / вызов известной безопасной функции) и ни на
  одном пути нет записи. **Обязан привести цепочку вызовов**, например:
  `флаг[0] читается в 0x1234 -> вызывает 0x5678 -> ветка A: return; ветка B: 0x9abc (только чтение регистра)`.
- **`ЕСТЬ ЗАПИСЬ`** — нашёл функцию записи. Указать адрес, куда пишет, и цепочку.
- **`НЕИЗВЕСТНО`** — не смог проследить. **Обязан указать, на чём именно остановился**
  (адрес функции, которую не разобрал, и почему).

**Формулировки «скорее всего», «вероятно», «не должно», «маловероятно» — ЗАПРЕЩЕНЫ
полностью.** Не как стилистическая придирка: такая фраза в отчёте о безопасности
читается как разрешение, не будучи им.

Если по всем десяти вышло `НЕИЗВЕСТНО` — **это нормальный результат задачи.** Честное
«не смог» полезнее выдуманного «безопасно».

### Шаг 1 — Найти потребителей флагов
Абсолютных ссылок на `0xc1510dc8` в `.text`, кроме записи, **нет** (проверено побайтово,
контроль на соседних адресах даёт 0 — метод рабочий). Значит потребители читают массив
**через вычисляемое смещение от базы**.

Что делать:
- определи, в каком регистре и от чего считается база при чтении;
- найди все места, где эта база загружается;
- отсюда выйди на читателей конкретных байт.

Если проследить не удалось — **так и напиши**, и переходи к шагу 2: для веток с
известными адресами (индекс 5 и ветки TEST MENU) анализ возможен и без этого.

### Шаг 2 — Разобрать явные ветки (это выполнимо гарантированно)
В теле функции есть ветвление по значению `r5`. Разбери **каждую** такую ветку и все
вызовы из неё — в первую очередь `0x81fd0` (индекс 5, `NODIST.SDK`), `0x1ab4c`,
`0x1acac`, `0x1ac3c`.

Для каждого вызова: что делает, вызывает ли что-то дальше, доходит ли до записи.
**Рекурсивно, до терминальной точки.**

### Шаг 3 — Составить список функций записи
Найди в прошивке функции, которые пишут в постоянную память, и запомни их адреса —
они нужны как «красные флажки» при обходе цепочек. Ищи по строкам и по обращениям к
диапазонам:
```
.camadj   0xdffa0000 .. 0xdffe0000
.camdef   0xdffe0000 .. 0xe0020000
```
Плюс строки вроде `flash`, `erase`, `write`, `sector`, `eeprom`, `adjust`, `calib`.

Если при обходе цепочки встретишь вызов такой функции — это `ЕСТЬ ЗАПИСЬ`.

### Шаг 4 — `WIFIDUMP.SDK` (индекс 7) отдельно
Самый интересный для нас: если он создаёт диагностический файл, мы получим данные,
которых иначе не достать. Выясни: создаёт ли файл, какое имя, что пишет.

Известные шаблоны имён файлов в прошивке:
```
.text 0x3d1274  L%04d-%02d.TXT   (рядом: AWB_DEBUG_MODE, SENSOR MODE=, EVAL PATTERN=)
.text 0x370800  OUT%05x.txt
.text 0x3d0350  data%d.txt
.text 0x113a3e  MSSAGE.DAT
```

### Шаг 5 — `NOSLEEP.SDK` (индекс 0) отдельно
Первый кандидат на живую проверку. Подтверди по коду, что он про отключение засыпания
(таймеры автовыключения, `auto power off`, `sleep`), и что записи на его пути нет.
