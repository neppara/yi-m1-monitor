# Анализ функции проверки SDK-режимов (task08)

## 1. Ответь по коду:
### Как проверяется наличие файла? Какую функцию она вызывает — открытие файла, поиск по каталогу, stat? Приведи адрес вызываемой функции.
Проверка выполняется в цикле, начинающемся по адресу `0x000ab8cc` (сама функция была разбита декомпилятором Ghidra на мелкие блоки, включая цикл по `0xabc0c`).
В цикле загружается указатель на строку из массива (по адресу `0xc09b4b24`), затем он передаётся в функцию подготовки строки `0x0030fa60`. После этого вызывается функция `0x0001aa70`, которая возвращает 1, если файл существует. Внутри `0x0001aa70` идёт обращение к системным функциям (вероятно, обёртка над `stat` или `fstat`, так как выделяется локальный буфер 88 байт для структуры, после чего вызывается системный обработчик). Самого чтения содержимого (`fopen` -> `fread`) в базовом цикле проверки не происходит.

### Где именно ищутся файлы — корень карты, подкаталог? Видна ли строка пути или имя тома?
В самом цикле по адресу `0x000ab8cc` константы путей (типа `D:\` или `A:\`) в явном виде не загружаются. Функция `0x0030fa60`, скорее всего, является аналогом `sprintf` или конкатенатором путей, который подставляет имя файла к корню SD-карты, используя буфер (переданный через `param_1`), однако точный том внутри базового блока не читается явно. Поведение типично для поиска в корневом каталоге карты памяти.

### Требуется ли содержимое файла, или достаточно самого факта существования? Читаются ли байты из него?
Для включения самих триггеров достаточно только факта существования файла. Функция `0x0001aa70` возвращает 1 или 0 (проверяется инструкцией `cmp r0, #1`). Байты из файлов в данном цикле не читаются.

### Как записывается результат в 0xc1510dc4/0xc1510dc8: битовая маска (какой бит какому индексу файла), массив байт, что-то ещё? Дай точную раскладку индекс→бит.
Результат записывается как **массив байт**, а не битовая маска. 
В коде есть инструкция:
```assembly
ldr r1, [0xabbb0]   ; R1 = 0xc1510dc8 (адрес массива флагов)
strb r0, [r1, r5]   ; сохранить результат проверки (1 или 0) по смещению R5 (индекс от 0 до 9)
```
Раскладка:
- Байт `0xc1510dc8 + 0`: индекс 0 (WIFIDUMP.SDK)
- Байт `0xc1510dc8 + 1`: индекс 1 (NOSLEEP.SDK)
и так далее.

### Что делают строки TEST MENU / PLAY TEST / DARK TEST / TSD TEST в этой же функции?
Внутри цикла, после записи флага существования файла, есть специальные проверки для некоторых индексов:
- `subs r0, r5, #5` — если индекс файла равен 5 (что соответствует одной из тест-строк, например, "DARK TEST"), вызывается специфическая функция `0x00081fd0`.
- `cmp r0, #2` — (что означает `r5 == 7`, например, "TSD TEST" или "TEST MENU"). Если это так, выполняется блок кода с вызовом дополнительных процедур инициализации (например, `FUN_0001ab4c`, `FUN_0001acac`), связанных с настройкой графического интерфейса тестовых меню.
Это значит, что помимо установки флага, для этих режимов немедленно инициализируются подсистемы камеры или UI.

## 2. Безопасны ли эти режимы для камеры?
Большинство из этих файлов (такие как `NOSLEEP.SDK` или `WIFIDUMP.SDK`) не выполняют запись в постоянную память (флеш) камеры, а лишь переключают флаги в RAM (`0xc1510dc8`), меняя поведение системы (например, отключая переход в спящий режим или включая расширенное логгирование WiFi).
- Режимы `AUDIOADJ`, `IMAGER`, `DARK TEST` могут запускать процедуры калибровки, однако без наличия специальных скриптов или подтверждений они, скорее всего, ограничатся выводом диагностической информации. 
Рекомендуется с осторожностью относиться к тестовым режимам (особенно TSD TEST и IMAGER), но само по себе создание пустых файлов-триггеров на SD-карте не должно привести к необратимым изменениям (окирпичиванию), так как они не прошивают камеру, а лишь активируют ветки кода в RAM.

## 3. Таблица и вывод (Self-critique)
| Режим SDK | Тип проверки | Уровень угрозы | Примечания |
|---|---|---|---|
| WIFIDUMP / NOSLEEP | stat (поиск файла) | Низкий | Только установка байт-флага в RAM, чтение не требуется |
| DARK TEST / TSD TEST | stat + вызов обработчика | Средний | Инициализируют UI тестового меню или процедуры калибровки |

Декомпиляция этого участка была осложнена тем, что Ghidra некорректно определила границы функции из-за наличия пула констант (data pool) внутри тела функции и восприняла цикл `0xabc0c` как множество мелких функций-переходников. Путем анализа дизассемблера и перекрестных ссылок (cross-references) удалось восстановить реальную логику работы функции с `0xab8cc`.
