## 1. Зачем эта задача — прочитай, это влияет на приоритеты

В прошивке найдены **10 имён файлов-триггеров** сервисных режимов. Механизм классический
для встраиваемых камер: прошивка при старте ищет файл с таким именем в корне SD-карты и,
найдя, включает соответствующий режим.

```
0x53117f  NOSLEEP.SDK     0x5311c4  AUDIOADJ.SDK
0x53118c  SLEEP1.SDK      0x5311d1  WIFIDUMP.SDK
0x531197  IMAGER.SDK      0x5311de  SHORTPIC.SDK
0x5311a2  BATLIFE.SDK     0x5311eb  SHORTMOV.SDK
0x5311ae  NONAIL.SDK
0x5311b9  NODIST.SDK
```

Рядом с ними — строки сервисного меню: `TEST MENU`, `PLAY TEST`, `DARK TEST`,
`TSD TEST`, а также `AF IESP`, `AF SPOT`, `AF TARGET`, `AF FACE`, `ONETOUCH WB`.

### ГЛАВНЫЙ ВОПРОС ЗАДАЧИ — БЕЗОПАСНОСТЬ

Человек собирается пробовать эти режимы на **своей единственной камере**. Часть имён
настораживает: `AUDIOADJ` — «adjustment», то есть **подстройка/калибровка**; `IMAGER`,
`NODIST` (дисторсия), `NONAIL` (миниатюры), `DARK TEST` (калибровка тёмного кадра).

В карте памяти есть области заводской калибровки: **`.camadj`** (`0xdffa0000`, 256 КБ) и
**`.camdef`** (`0xdffe0000`, 256 КБ). Если какой-то режим их перезаписывает — откатить
будет нечем, камера навсегда останется с испорченной калибровкой.

**Поэтому вопрос №1: какие из этих режимов ПИШУТ куда-либо (в калибровку, во флеш, в
настройки), а какие только меняют поведение в оперативной памяти.**

Если по какому-то режиму не удалось выяснить — так и пиши, он останется в списке
«не трогать». Это нормальный и полезный ответ.

## 2. Что уже установлено (данность, перепроверять не нужно)

- **Таблица указателей** на 10 имён: `.data` по адресу **`0xc09b4b24`**, 10 подряд
  идущих 32-битных указателей. Сразу за ней (с `0xc09b4b4c`) — отдельная таблица из
  20 названий режимов (`DIAL MODE`, `ISO MODE`, ...), не путать.
- **Единственная ссылка** на эту таблицу: `.text` по адресу **`0xabbac`** (константа в
  пуле). Тело функции начинается примерно с `0xabb60`.
- В коде читается цикл:
  ```
  0xabc0c  e2855001   ADD  R5, R5, #1
  0xabc10  e355000a   CMP  R5, #0xA      <- ровно 10 итераций
  ```
- В том же пуле констант лежат:
  ```
  0xabbb0 -> 0xc1510dc8  (.bss)
  0xabbb8 -> 0xc1510dc4  (.bss)
  0xabbd4 -> 0xc1401074  (.bss)
  0xabbc4..0xabbd0 -> 'TEST MENU', 'PLAY TEST', 'DARK TEST', 'TSD  TEST'
  ```
- Проверено побайтовым поиском: на `0xc1510dc4` и `0xc1510dc8` во всём `.text`
  **по одной ссылке** — только отсюда. На `0xc1401074` — **223 ссылки** (это, судя по
  всему, общая база системного состояния, а не наш флаг). Контроль на соседних адресах
  `.bss` даёт 0 ссылок, то есть метод поиска рабочий.

**Отсюда вывод, который надо развить:** потребители флагов обращаются к ним не по
абсолютному адресу, а **через вычисляемое смещение от базы**. Байтовым поиском эту
цепочку не проследить — нужен декомпилятор. Это и есть твоя основная работа.

## 3. Окружение и загрузка

```
Ghidra:     /opt/homebrew/Cellar/ghidra/12.1.2/libexec/support/analyzeHeadless
JAVA_HOME:  /opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home
```
`JAVA_HOME` **обязательно** экспортировать перед каждым вызовом.

### Загружай ВСЕ ТРИ секции в ОДНУ программу
```
1. Импорт: research/YI-M1-firmware-3.2-int/3.2-int/firmware.bin.0.00008192.decompressed
   -processor "ARM:LE:32:v5t"   (без суффикса :default)
   -loader BinaryLoader  -loader-baseAddr 0x00002000

2. Через -postScript (Memory.createInitializedBlock), в ТУ ЖЕ программу:
   .rodata <- firmware.bin.0.03127296.decompressed  @ 0x0043f800
   .data   <- firmware.bin.0.07251968.decompressed  @ 0xc09b0000
```
**Не отдельными `-import`** — иначе программы изолированы и xref не сойдутся.
Подробности и полная карта секций: `fable research/firmware-memory-map.md`.

**Санити-чек:** строка `"RCVideoFormatSet"` по `0x006b866c`; блок `.data` читается.

### Известные грабли
Автоанализ портит границы функций и ложно метит их «non-returning». Лечится по
возрастанию надёжности: `setNoReturn(false)` → снять `FlowOverride` с CALL-инструкций →
задать тело явно через `FunctionManager.createFunction(...)`, исключив пул констант.

**Отдельно предупреждение:** Ghidra на этом образе **не строит xref на строки** даже с
загруженной `.data` (проверено в задаче 07 — контроль на заведомо используемом `MF`
тоже дал ноль ссылок). Не делай выводов из отсутствия xref. Работай от кода функции.

## 4. Что сделать

### Шаг 1 — Разобрать функцию проверки (главное)
Определи границы функции, содержащей `0xabbac` (начало примерно `0xabb60`), и
**декомпилируй её полностью**. Приведи код в отчёте как есть.

Ответь по коду:
1. **Как проверяется наличие файла?** Какую функцию она вызывает — открытие файла,
   поиск по каталогу, `stat`? Приведи адрес вызываемой функции.
2. **Где именно ищутся файлы** — корень карты, подкаталог? Видна ли строка пути или
   имя тома?
3. **Требуется ли содержимое файла**, или достаточно самого факта существования?
   Читаются ли байты из него?
4. **Как записывается результат** в `0xc1510dc4`/`0xc1510dc8`: битовая маска (какой бит
   какому индексу файла), массив байт, что-то ещё? **Дай точную раскладку индекс→бит.**
5. Что делают строки `TEST MENU`/`PLAY TEST`/`DARK TEST`/`TSD TEST` в этой же функции —
   это отдельная ветка, пункты меню, или условие входа в сервисный режим?

### Шаг 2 — БЕЗОПАСНОСТЬ (по важности — первый)
Проследи, куда уходят флаги. Раз абсолютных ссылок нет, ищи через базовый регистр:
определи, от какого базового указателя считается доступ, и найди других потребителей
этой базы.

Для **каждого** из 10 режимов ответь на вопрос:

> **Меняет ли он только поведение в RAM, или что-то ЗАПИСЫВАЕТ (калибровку, настройки,
> флеш)?**

Особое внимание: обращения к областям **`.camadj` (`0xdffa0000`)** и
**`.camdef` (`0xdffe0000`)**, а также к любым функциям записи во флеш/EEPROM.

Заполни таблицу — она главный результат задачи:

| Файл | Что делает (по коду) | Пишет куда-либо? | Уверенность |
|---|---|---|---|

**Колонку «пишет куда-либо» заполняй консервативно.** Если не удалось проследить —
пиши «НЕИЗВЕСТНО», а не «нет». Разница принципиальная: «нет» человек прочитает как
разрешение пробовать.

### Шаг 3 — `WIFIDUMP.SDK` отдельно
Самый интересный для нас режим: если он создаёт диагностический файл, мы получим данные,
которых иначе не достать (в том числе, возможно, про инициализацию объектива).

Выясни: создаёт ли он файл, какое имя/шаблон, куда пишет, что именно.

Полезные зацепки — шаблоны имён файлов, уже найденные в прошивке:
```
.text 0x3d1274  L%04d-%02d.TXT     (рядом: AWB_DEBUG_MODE, SENSOR MODE=, EVAL PATTERN=)
.text 0x370800  OUT%05x.txt
.text 0x3d0350  data%d.txt
.text 0x113a3e  MSSAGE.DAT         (рядом: 'WRONG MSSAGE.DAT', 'NG JUDGE FILE ERR')
```

### Шаг 4 — `NOSLEEP.SDK` отдельно
Первый кандидат на живую проверку. Подтверди по коду, что он действительно про
отключение засыпания (ищи таймеры автовыключения, `auto power off`, `sleep`), и что он
ничего не записывает.

### Раздел 6 — «КРИТИКА СОБСТВЕННОГО ВЫВОДА» (обязателен)
**Минимум три конкретные причины**, по которым твои выводы о безопасности могут быть
неверны. Предметно: какую ветку кода ты не проследил, где декомпилятор мог соврать, для
какого режима вывод самый шаткий. Не можешь придумать три — значит, недостаточно
проверял. Помни: по этому разделу человек решает, рисковать ли камерой.

### Правила
- Адреса — **полностью**, без сокращений.
- Все команды и скрипты — **дословно**, чтобы повторить.
- Непроверенное помечай `ГИПОТЕЗА:`. «Вероятно», «скорее всего», «должно быть» без
  этого префикса **запрещены**.
- Декомпилированный код приводи **как есть**, не «причёсывая».
- **Никогда не пиши «безопасно», если не проследил все пути записи.** Правильная
  формулировка в таком случае — «путей записи не обнаружено, но ветка X не разобрана».
