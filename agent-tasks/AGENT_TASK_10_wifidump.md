## 1. ГЛАВНОЕ ПРАВИЛО ЭТОЙ ЗАДАЧИ: не выдумывать строки

В предыдущем заходе (задача 09) отчёт утверждал, что режим `NODIST.SDK` передаёт в
функцию логирования строки `DIST_ALL_OFF`, `DIST_ON`, `DIST_THR_OFF`.

**Ни одной из этих строк не существует** — проверено точным побайтовым поиском по всем
трём секциям (`.text`, `.rodata`, `.data`). Их нет. Вердикт по этому режиму пришлось
аннулировать, хотя формально отчёт выглядел убедительно.

**Поэтому жёсткое требование:**

> Каждая строка, которую ты цитируешь в отчёте, приводится **вместе с адресом**, по
> которому она лежит. Формат: `` `TEXT` @ 0xADDRESS (.section) ``.
> Строка без адреса в отчёте = ошибка отчёта.

Перед тем как процитировать строку — **прочитай байты по адресу и убедись**, что там
именно она. Если строку найти не удалось, пиши «строк не обнаружено», а не придумывай
правдоподобные.

Это не придирка к оформлению: адрес делает утверждение проверяемым за десять секунд, а
выдумку — заметной. Проверять будут.

## 2. Задача

Выяснить, **что делает режим `WIFIDUMP.SDK`** (индекс 7) и, главное:
**создаёт ли он файл, и если да — какой и с каким содержимым.**

Зачем: если режим выгружает диагностику на карту, мы получим данные, которых иначе не
достать. В прошивке есть встроенная трассировка загрузки с метками
`BT_LENS_INIT_START` / `BT_LENS_INIT_END` (`.rodata` рядом с `0x43fcc5`), а у владельца
камеры **электронно не опознаётся объектив**. Если дамп содержит этапы загрузки, по нему
можно будет увидеть, на чём именно спотыкается инициализация объектива.

## 3. Что уже установлено — принимай как данность

Всё ниже проверено вручную чтением байт и дизассемблера.

### Механизм триггеров
Функция `0x000ab8cc` в цикле по 10 итерациям проверяет наличие файлов на карте и
складывает результат в **массив байт** по адресу `0xc1510dc8`, по одному байту на файл:

```
0xab8dc  e7941105   LDR  r1, [r4, r5, LSL #2]   ; имя файла № r5 из таблицы 0xc09b4b24
0xab8e0  eb09905e   BL   0x30fa60               ; подготовка строки/пути
0xab8e8  ebfdbc60   BL   0x1aa70                ; проверка существования (возвращает 0/1)
0xab8f8  e7c10005   STRB r0, [r1, r5]           ; флаг: байт по индексу r5
```
Содержимое файла **не читается** — достаточно факта существования.

### Раскладка индексов (сверена с байтами таблицы `0xc09b4b24`)
```
0 NOSLEEP.SDK   1 SLEEP1.SDK   2 IMAGER.SDK    3 BATLIFE.SDK   4 NONAIL.SDK
5 NODIST.SDK    6 AUDIOADJ.SDK 7 WIFIDUMP.SDK  8 SHORTPIC.SDK  9 SHORTMOV.SDK
```

### Геттер флагов — ключ ко всему
```
0xab97c  e59f122c   LDR   r1, [pc, #0x22c]   ; база массива флагов
0xab980  e19100d0   LDRSB r0, [r1, r0]       ; вернуть flags[index]
0xab984  e12fff1e   BX    LR
```
Весь остальной код читает флаги **только через эту функцию** — поэтому абсолютных
ссылок на `0xc1510dc8` нигде и нет.

### ПОЛНЫЙ список вызовов геттера — 18 штук
Задача 09 нашла 16 и пропустила два. Вот выверенный список (пересчитан побайтово по
всем BL во всём `.text`):

```
0x17ce8   0x1d744   0x21874   0x219d0   0x21fe4   0x22104
0x2224c   0x24e48   0x24ff4   0x81fd8   0x87608   0xa8b3c
0xa8b54   0xac2cc   0xacd8c   0xacf38   0xd7b70   0xd7bc8
```

**Пропущенные ранее `0x2224c` и `0xacd8c` важны:** `0xacd8c` стоит вплотную к тем, что
были отнесены к `WIFIDUMP` (`0xac2cc`, `0xacf38`). То есть анализ именно нашего режима в
прошлый раз вёлся по неполному списку.

## 4. Что сделать

### Шаг 1 — Определить, какие вызовы геттера относятся к индексу 7
Из 18 мест надо понять, какие спрашивают именно флаг `WIFIDUMP` (аргумент `r0 == 7`).

Для каждого из трёх кандидатов — **`0xac2cc`, `0xacd8c`, `0xacf38`** — посмотри, какое
значение кладётся в `r0` перед вызовом (обычно `MOV r0, #7` непосредственно перед `BL`).
Подтверди или опровергни принадлежность каждого.

Если найдёшь ещё вызовы с аргументом 7 в остальном списке — включи их тоже.

### Шаг 2 — Проследить, что происходит при флаге = 1
Для каждого подтверждённого места: разбери ветку, которая выполняется при взведённом
флаге. Рекурсивно, до терминальной точки (возврат / бесконечный цикл / вызов уже
разобранной функции).

Отвечай по коду на:
1. **Открывается ли файл на запись?** Какая функция, по какому адресу.
2. **Какое имя файла** и откуда оно берётся — константа, `sprintf`-шаблон, счётчик?
3. **Что пишется** — текст, бинарь? Видны ли форматные строки?
4. **Когда это происходит** — при старте, по событию, постоянно?

### Шаг 3 — Связать с известными шаблонами имён
В прошивке уже найдены шаблоны имён файлов. **Проверь, использует ли `WIFIDUMP`
какой-то из них** (или совсем другой):

### Шаг 4 — Функции работы с файлами
Найди в прошивке функции открытия/записи файла (аналоги `fopen`/`fwrite`/`fprintf`) и
приведи их адреса. Они нужны как ориентиры при обходе цепочек — и пригодятся для
следующих задач.

Подсказка: функция проверки существования файла — `0x1aa70`, подготовки строки —
`0x30fa60`. Соседние функции в тех же диапазонах, вероятно, из того же файлового слоя.

### Шаг 5 (если останется время) — безопасность остальных режимов
В задаче 09 шесть режимов получили вердикт `НЕИЗВЕСТНО`. Если справишься с основным

### Раздел 7 обязателен
**Минимум три конкретные причины**, по которым выводы могут быть неверны. Предметно:
какую ветку не дочитал, где декомпилятор мог соврать, какой вывод самый шаткий.

### Правила отчёта
- **Каждая цитируемая строка — с адресом и секцией.** Без адреса не приводить.
- Адреса — полностью, без сокращений.
- Все команды и скрипты — дословно.
- Непроверенное помечай `ГИПОТЕЗА:`. «Вероятно», «скорее всего», «должно быть»
  без этого префикса **запрещены**.
- Декомпилированный код приводи как есть, не «причёсывая».
- Если что-то не нашёл — так и пиши. **Ненайденное лучше выдуманного:** выдумку
  всё равно обнаружат при проверке, а доверие к остальному отчёту она обнулит.
