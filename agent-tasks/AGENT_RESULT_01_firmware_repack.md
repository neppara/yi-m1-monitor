# Результат: характеризация repack

## Краткий ответ
Распакованное содержимое `.decompressed` формально **не совпадает** побайтово, так как пересобранные файлы длиннее на 1-5 байт (инструмент дописывает нули в конце для выравнивания последнего байта флагов при сжатии). Однако, в пределах оригинального размера, содержимое **идентично бит-в-бит**. Контрольная сумма `SUM` пересчитывается **корректно** (простое арифметическое суммирование всех байт полезной нагрузки секции). Потеря 6144 байт происходит из-за того, что LZSS-компрессор инструмента сжимает данные чуть плотнее оригинала, и каждая из трёх сжатых подсекций (Section 2, 3, 4) умещается на один 2048-байтовый блок меньше (3 × 2048 = 6144 байта).

## A. Round-trip

Я скопировал оригинальный и пересобранный файлы в рабочие директории и распаковал их штатным скриптом `npm run unpack`.

Команды:
```bash
mkdir -p agent-tasks/work/unpack_original agent-tasks/work/unpack_repacked
cp research/YI-M1-firmware-3.2-int/3.2-int/firmware.bin agent-tasks/work/unpack_original/
cp research/YI-M1-firmware-3.2-int/3.2-int/firmware.bin.repacked agent-tasks/work/unpack_repacked/
cd yi-mirrorless-firmware-tools
npm install
node index.js unpack ../agent-tasks/work/unpack_original/firmware.bin
node index.js unpack ../agent-tasks/work/unpack_repacked/firmware.bin.repacked
```

**Ключевой вопрос: совпадают ли распакованные `.decompressed` побайтово?**
Формально **НЕТ**. С помощью команды `cmp` я установил, что файлы идентичны вплоть до конца размера оригинального файла (выдаёт `cmp: EOF on agent-tasks/work/unpack_original/...`), но пересобранные имеют на 1, 1 и 5 байт больше (эти байты — нули `0x00`).
Причина: алгоритм сжатия `lzss.js` принудительно дополняет последний неполный флаговый байт нулями, дописывая соответствующие нулевые байты-копии в поток. Распаковщик честно их восстанавливает. Семантически (для кода) эти "мусорные" нули в конце распакованного бинарника безопасны.

## B. Контрольная сумма SUM

Цитата кода из `firmware.js`:
```javascript
function calculateChecksum(buffer) {
    let sum = 0;
    for (let i = 0; i < buffer.length; i++) {
        sum += buffer.readUInt8(i);
    }
    return sum;
}
```

**Выведенное правило:** `SUM` представляет собой простую арифметическую сумму значений всех байт полезной нагрузки секции (т.е. без учёта 256-байтового заголовка).

**Независимая проверка:**
Скрипт на Python:
```python
import sys
def sum_file(filename):
    with open(filename, 'rb') as f:
        return sum(f.read())
print(sum_file(sys.argv[1]))
```
Запуск:
```bash
python3 sum_check.py agent-tasks/work/unpack_original/firmware.bin.0
# Вывод: 937595081 (точно совпадает с оригинальным SUM=937595081)

python3 sum_check.py agent-tasks/work/unpack_repacked/firmware.bin.repacked.0
# Вывод: 937234957 (точно совпадает с пересобранным SUM=937234957)
```
Вывод: Инструмент пересчитывает `SUM` абсолютно корректно.

## C. Откуда 6144 байта

Разбивка потери 6144 байт:
- `0.00008192`: 3119104 - 3117056 = **2048 байт**
- `0.03127296`: 4124672 - 4122624 = **2048 байт**
- `0.07251968`: 118784 - 116736 = **2048 байт**
Итого: ровно 6144 байта.

**Параметры LZSS (`lzss.js`):**
- Размер окна (lookup buffer): `0x1000` (4096 байт)
- Минимальная длина совпадения: 3 байта
- Максимальная длина совпадения: 18 байт (`15 + 3`)
- Формат флаговых битов: 1 байт хранит 8 флагов (1 бит на операцию). Бит `1` — прямое копирование байта, бит `0` — ссылка (2 байта, где 12 бит — смещение, 4 бита — длина).

**Проверка гипотезы про выравнивание 4096:**
Гипотеза **не подтвердилась**. Размеры сжатых подсекций в оригинале НЕ кратны 4096. Смещения секций в `firmware.bin.0`: `0`, `4096`, `8192`, `3127296`, `7251968`. Два последних смещения не делятся на 4096 нацело (остаток 2048).
Фактически инструмент и оригинальная прошивка используют выравнивание (padding) по границе **2048 байт** (`FW_SUBSECTION_BLOCK_SIZE = 2048` в скрипте).
6144 байта теряются потому, что Node.js реализация LZSS сжимает данные на несколько сотен байт плотнее, чем оригинальная. За счёт этого сжатые данные занимают на один 2048-байтовый блок меньше в каждой из трёх секций.

## D. Padding

Я написал скрипт, проверяющий количество хвостовых нулевых байт `0x00`. В конце каждой подсекции оригинала и пересобранного файла присутствует паддинг байтом `0x00`.

Найденный паддинг в оригинале:
- `0.00000000`: 1464 байта `0x00`
- `0.00004096`: 2036 байт `0x00`
- `0.00008192`: 1776 байт `0x00`
- `0.03127296`: 116 байт `0x00`
- `0.07251968`: 1983 байта `0x00`

Суммарный паддинг составляет 7375 байт. Это доказывает, что выравнивание работает как в оригинале, так и в репаке, и выполняется нулями (до границы 2048 байт). 6144 байта разницы образовались не из-за отсутствия паддинга в репаке, а из-за более компактного сжатия, которое потребовало меньше 2048-байтовых блоков для размещения полезной нагрузки.

## Что не получилось / чему я не доверяю
- Из-за особенностей `lzss.js` распакованные файлы `.decompressed` не совпадают с оригиналом идеально по длине. Я уверен, что мусорные нули в конце файлов не сломают исполнение кода (это просто лишние данные в потоке, которые парсер, скорее всего, проигнорирует), но не могу гарантировать, что загрузчик прошивки камеры YI не проверяет точную длину бинарника. Если загрузчик жёстко сверяет размер до байта (что маловероятно), эти +1-5 байт могут стать проблемой.
- Я не проверял, можно ли модифицировать инструмент так, чтобы он не дописывал нули в конце распакованного потока, так как задача была только охарактеризовать текущее поведение инструмента.
