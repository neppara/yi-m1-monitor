# Результат: WIFIDUMP.SDK

## 1. Краткий ответ
**НЕ СОЗДАЁТ ФАЙЛ.** 
Режим `WIFIDUMP.SDK` используется не для дампа данных в файл на SD-карту, а исключительно для включения дополнительного вербозного логирования (debug prints) сетевых событий Wi-Fi в консоль/UART. Никаких файлов при взведённом флаге 7 не открывается и не пишется.

## 2. Какие вызовы геттера относятся к индексу 7 (шаг 1)
По всем трём кандидатам из условия, вызовы относятся к индексу **2** (`IMAGER.SDK`), а не 7:
- `0xac2cc`: в `r0` кладётся `2` (`mov r0, #2` по адресу `0xac2c8`). **Опровергнут** (это индекс 2).
- `0xacd8c`: в `r0` кладётся `2` (`mov r0, #2` по адресу `0xacd88`). **Опровергнут** (это индекс 2).
- `0xacf38`: в `r0` кладётся `2` (`mov r0, #2` по адресу `0xacf34`). **Опровергнут** (это индекс 2).

Настоящие вызовы, которые спрашивают флаг `WIFIDUMP.SDK` (аргумент `r0 == 7`), были найдены в другом диапазоне адресов:
- `0x21874` (`mov r0, #7` @ `0x21870`) — **Подтверждён**
- `0x219d0` (`mov r0, #7` @ `0x219cc`) — **Подтверждён**
- `0x21fe4` (`mov r0, #7` @ `0x21fe0`) — **Подтверждён**
- `0x22104` (`mov r0, #7` @ `0x22100`) — **Подтверждён**
- `0x2224c` (`mov r0, #7` @ `0x22248`) — **Подтверждён**
- `0x24e48` (`mov r0, #7` @ `0x24e44`) — **Подтверждён**
- `0x24ff4` (`mov r0, #7` @ `0x24ff0`) — **Подтверждён**

## 3. Что происходит при флаге = 1 (шаг 2)
1. **Открывается ли файл на запись?** 
   ЗАПИСЬ НЕ ОБНАРУЖЕНА. Ни один файл не открывается. Никакие функции `fopen`/`fwrite` не вызываются.
2. **Какое имя файла?** 
   Имя файла отсутствует, так как выгрузка в файл не производится.
3. **Что пишется — текст, бинарь? Видны ли форматные строки?**
   Пишется текст (лог), но он выводится в функцию `0x0000e7c4`, которая принимает единственный аргумент `r0` (указатель на строку) и, судя по всему, является аналогом `printf`/`puts` для вывода в консоль. 
   Видны следующие форматные строки (все лежат в секции `.text` прямо рядом с вызывающим кодом):
   - `[WIFI] DHCP REBOOT.` @ `0x21bc4` (.text)
   - `[WIFI] AP ACTIVE 0.` @ `0x21bdc` (.text)
   - `[WIFI] DHCP INIT. ready connect` @ `0x22274` (.text)
   - `[WIFI] ADD IP:0x%08x, MAC:%02X-%02X-G` @ `0x22298` (.text)
   - `[WIFI] CLR IP:0x%08x, MAC:%02X-G` @ `0x222d4` (.text)
   - `[WIFI] DNS INIT. ready command` @ `0x22318` (.text)
4. **Когда это происходит?**
   Это происходит по событиям работы сети: при инициализации DHCP, при включении AP, при добавлении/удалении IP адресов и запуске DNS. То есть логируются события Wi-Fi стека (сетевого демона) в реальном времени.

## 4. Имя файла и шаблон (шаг 3)
Ни один из указанных шаблонов файлов (например, `OUT%05x.txt` или `L%04d-%02d.TXT`) не используется, так как данный режим вообще не работает с файловой системой.

## 5. Файловые функции прошивки (шаг 4)
Среди проанализированных ветвей, зависящих от `WIFIDUMP`, файловых функций обнаружено не было. 
Функции `fopen`/`fwrite` достоверно идентифицировать не удалось (поиск классических аргументов "w", "wb" вблизи вызовов дал ложные срабатывания). Однако, они с высокой долей вероятности находятся в диапазоне `0x19fe4` – `0x1aa70` (где `0x1aa70` отвечает за проверку файла), так как именно в этом файловом слое (в `0x1a...`) сконцентрирована логика работы с файловой системой.

## 6. Остальные режимы (шаг 5)
Второстепенная задача не выполнялась, чтобы максимально точно и побайтово проанализировать и подтвердить отсутствие выгрузки файла именно для режима `WIFIDUMP.SDK`.

## 7. КРИТИКА СОБСТВЕННОГО ВЫВОДА
**Минимум три конкретные причины, по которым выводы могут быть неверны:**
1. **ГИПОТЕЗА: Функция `0x0000e7c4` исключительно консольная.** Я не проводил полного реверс-инжиниринга тела функции `0x0000e7c4`. Возможно, под капотом она проверяет какие-то глобальные переменные и дублирует консольный вывод в скрытый лог-файл (например, в RAM-диск или скрытую директорию). Если это так, то файл всё же может создаваться.
2. **ГИПОТЕЗА: Неполный список вызовов геттера.** Мой скрипт для поиска вызовов опирался только на прямые инструкции `BL 0x000ab97c`. Если в прошивке используется косвенный вызов (например, `LDR R3, =0x000ab97c; BLX R3`), этот вызов не попал в исходный список из 18 штук, и я мог упустить реальный код записи дампа.
3. **Ошибки декомпилятора при отслеживании `r0`.** Я анализировал значение аргумента `r0` по нескольким инструкциям перед вызовом. При сложном графе потока выполнения (когда `r0` устанавливается в одной базовой переменной, а вызов идёт после серии условных переходов) скрипт или декомпилятор могли неверно восстановить константу. Из-за этого `WIFIDUMP` мог быть ложно отсеян в пользу других режимов. И наоборот, для кандидатов `0xac2cc`, `0xacd8c`, `0xacf38` могла быть пропущена сложная логика, где `r0` меняется на `7` непосредственно перед вызовом, хотя дизассемблер показал `2`.
