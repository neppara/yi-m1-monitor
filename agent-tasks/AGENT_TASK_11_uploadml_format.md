## 1. Контекст: документирование формата HTTP-API для совместимости

Это часть работы по документированию HTTP-протокола камеры, чтобы наши приложения-
компаньоны (`yi-m1-remote-control`, `yi-m1-ios`) корректно с ним работали. Мы уже
разобрали и задокументировали большинство команд (`RCISOSet`, `RCVideoFormatSet`,
`GetFileList` и др.) — их имена параметров, форматы значений, коды ответов.

Одна команда семейства «ML» осталась недокументированной: **`UploadML`**. Мы знаем
только имя из таблицы команд. Соседние команды семейства уже понятны:
- `GetMLFileList` — возвращает список (проверено вживую: `{"code":200,"data":[]}`);
- `DeleteMLFile` — удаление;
- в прошивке есть строки `select mlpic err` / `erase mlpic err`, то есть «ML»
  относится к изображениям (`mlpic` = ML picture).

**Задача — по коду обработчика определить формат запроса `UploadML`:** какие поля он
разбирает, куда сохраняет данные, какие ограничения накладывает. Это нужно, чтобы
понимать поведение команды и корректно её описать в документации протокола, а также
чтобы приложение не отправило некорректный запрос.

Наш HTTP-транспорт устроен так: команды идут как `GET /?data=<json>`. Но `UploadML`
по имени предполагает передачу данных, а в прошивке для HTTP-сервера найдены строки
разбора `multipart/form-data` (`form-data;`, `name=`, `filename=`, `Content-Type:`).
Поэтому важный подвопрос: **через какой транспорт передаётся тело — тот же GET, или
POST с multipart?**

## 2. Что уже установлено — принимай как данность

- **Обработчик `UploadML`** — адрес **`0x00155544`** (из таблицы команд `0x6b86ac`).
- Строки семейства: `UploadML` @ `0x6b859a`, `GetMLFileList` @ `0x6b84ca`,
  `DeleteMLFile` @ `0x6b8575` (все в `.rodata`).
- Строки ошибок: `select mlpic err` @ `0x6b81cc`, `erase mlpic err` @ `0x6b81dd`.
- Строки multipart-разбора в HTTP-сервере: `form-data;`, `name=`, `filename=`,
  `Content-Type:` — лежат непрерывным блоком в `.data` около `0xc09b0800`.
- Таблица HTTP-методов: `GET, POST, OPTIONS, HEAD, PUT, DELETE, TRACE, CONNECT`
  @ `.data` `0xc09f79ec`. (Наличие метода в таблице не значит, что команда его
  использует — это может быть общая таблица HTTP-библиотеки. Проверять по факту.)
- Как разбирается тело обычных команд (для сравнения): диспетчер `0x0015674c`
  извлекает JSON-поля через `0x001601f4`; имена ключей сравниваются функцией
  `0x001900c0`.

## 3. Что выяснить

### Вопрос 1 — Какие поля разбирает `UploadML`
Декомпилируй обработчик `0x00155544` полностью. Определи, какие именованные поля он
читает из запроса. Для каждого поля — имя строки и её адрес (`.section`).

Кандидаты по аналогии с другими командами: `path`, `name`, `filename`, `size`,
`Content-Type`. Но не подставляй их — **прочитай из кода**, что он реально ищет.

### Вопрос 2 — Куда сохраняются данные
Проследи, куда обработчик записывает принятое. Ответь:
- вызывает ли он функцию **создания/записи файла** (адрес);
- **имя или путь назначения** — задан жёстко (константа/шаблон в коде) или берётся из
  поля запроса? Если из запроса — из какого поля;
- есть ли ограничение на **каталог назначения** (например, всегда некий подкаталог), или
  путь произвольный.

Это ключевой вопрос: определяет, насколько гибок формат. Отвечай строго по коду.

### Вопрос 3 — Транспорт: GET или POST/multipart
Определи, ожидает ли обработчик тело в multipart-форме. Признаки: обращение к
функциям, которые работают со строками `form-data;` / `filename=` / `Content-Type:`
(около `0xc09b0800`), или к разбору тела POST. Проследи, вызывает ли путь `UploadML`
такие функции, или он читает поля тем же способом, что и обычные GET-команды (через
`0x0015674c` / `0x001601f4`).

### Вопрос 4 — Ограничения и проверки
Какие проверки выполняет обработчик перед сохранением: тип содержимого, ограничение
размера, проверка расширения/имени, проверка каталога? Приведи по коду. Если проверок
нет — так и укажи.

### Вопрос 5 — Функции файлового слоя
Побочно, но полезно для документации: определи адреса функций **создания и записи
файла** (аналоги `fopen`/`fwrite`), которые вызывает этот путь. Известно: проверка
существования файла — `0x1aa70`, подготовка строки пути — `0x30fa60`; функции записи,
скорее всего, в том же файловом слое `0x0001a...`.

### Раздел 8 обязателен
**Минимум три конкретные причины**, по которым выводы могут быть неверны. Предметно:
какую ветку не дочитал, где декомпилятор мог соврать, какой вывод самый шаткий.

### Правила отчёта
- **Каждая цитируемая строка — с адресом и секцией** (`` `TEXT` @ 0xADDR (.section) ``).
  Строка без адреса не приводится. Перед цитированием — прочитай байты и убедись.
- Адреса — полностью, без сокращений.
- Непроверенное помечай `ГИПОТЕЗА:`. «Вероятно», «скорее всего», «должно быть» без
  этого префикса **запрещены**.
- Декомпилированный код приводи как есть.
- Ненайденное лучше выдуманного. Выдуманную строку обнаружат при проверке по адресу.
