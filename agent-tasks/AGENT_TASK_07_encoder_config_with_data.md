## 1. Почему эта задача — повтор, и что изменилось

Предыдущая попытка (`AGENT_RESULT_06`) **провалилась по объективной причине**, а не
из-за плохой работы. Главный её вывод был: «прямых 32-битных указателей на строки
`4K_30` и `4K_30_LOW` не найдено, xref не строятся».

**Причина найдена: мы грузили в Ghidra только 2 секции из 3.**

В подсекции `firmware.bin.0.00004096` лежит таблица загрузки секций прошивки. Из неё
извлечена полная карта памяти камеры. Три секции содержат реальные данные:

| Секция | RAM-адрес | Длина | Файл | Грузили раньше? |
|---|---|---|---|---|
| `.text` | `0x00002000` | 4 445 304 | `firmware.bin.0.00008192.decompressed` | да |
| `.rodata` | `0x0043f800` | 5 703 196 | `firmware.bin.0.03127296.decompressed` | да |
| **`.data`** | **`0xc09b0000`** | **339 536** | **`firmware.bin.0.07251968.decompressed`** | **НЕТ** |

Размер файла `.data` — 339 542 байта против заявленных 339 536: разница в 6 байт это
известный артефакт распаковщика (хвостовые нули), такой же есть у `.text` (+1) и
`.rodata` (+2). Соответствие однозначное.

**`.data` — это инициализированные данные, то есть именно там живут таблицы указателей.**
Отсюда и «нет ссылок на строки»: они есть, просто в секции, которой в проекте не было.

Дополнительное подтверждение: ручная проверка показала, что на **заведомо
используемые** значения (`MF`, `S-AF`, `C-AF` — рабочие режимы фокуса) 32-битных
ссылок в `.text`/`.rodata` тоже нет. То есть отсутствие ссылок ничего не говорило о
строке — это была особенность неполной загрузки, а не свойство прошивки.

**Твоя задача: повторить поиск, загрузив все три секции.**

## 2. Цель

Найти, **где задаются параметры видеоэнкодера**: битрейт, профиль H.264, лимит
длительности записи.

Зачем: камера пишет H.264 **Constrained Baseline** (подтверждено `ffprobe` на реальных
файлах: `profile=Constrained Baseline, level=41`) — самый примитивный профиль, без
B-кадров и CABAC. Переход на High profile дал бы заметный прирост качества **на том же
битрейте**. Это то, чего годами просило сообщество.

## 3. Измеренные данные (данность)

| Режим | Разрешение | Битрейт |
|---|---|---|
| `FHD_30` | 1920×1080 | ~15.5 Мбит/с |
| `FHD_24` | 1920×1080 | ~15.9 Мбит/с |
| `720P_24` | 1280×720 | ~2.6 Мбит/с |

Лимиты: **4 ГБ** на файл (в 4K это ~7:29), около **30 минут** общий потолок.

## 4. Окружение и ЗАГРУЗКА (главное отличие от прошлой задачи)

```
Ghidra:     /opt/homebrew/Cellar/ghidra/12.1.2/libexec/support/analyzeHeadless
JAVA_HOME:  /opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home
```
`JAVA_HOME` **обязательно** экспортировать перед каждым вызовом.

### Рецепт загрузки ТРЁХ секций
1. Импортируй `research/YI-M1-firmware-3.2-int/3.2-int/firmware.bin.0.00008192.decompressed`:
   `-processor "ARM:LE:32:v5t"` (**без** суффикса `:default`), `-loader BinaryLoader`,
   `-loader-baseAddr 0x00002000`.
2. Через `-postScript` с Java-скриптом добавь **в ТУ ЖЕ программу** два блока памяти
   (`Memory.createInitializedBlock`), читая байты из файлов:
   - `.rodata` ← `firmware.bin.0.03127296.decompressed` по адресу **`0x0043f800`**
   - `.data`   ← `firmware.bin.0.07251968.decompressed` по адресу **`0xc09b0000`**  ← НОВОЕ
3. **НЕ используй отдельные `-import`** — иначе это разные «программы» без общих xref.
4. Анализ включён по умолчанию.

### Санити-чеки — сделай ОБА до основной работы
- строка `"RCVideoFormatSet"` по адресу `0x006b866c` (проверка `.rodata`);
- блок `.data` существует, читается, и по `0xc09b0000` лежат ненулевые байты.

Если `.data` не встала — останавливайся и пиши об этом, дальше идти бессмысленно.

### Грабли Ghidra на этом образе
Автоанализ портит границы части функций и ложно метит их «non-returning», из-за чего
декомпилятор обрезает тела. Лечится по возрастанию надёжности: `setNoReturn(false)` →
снять `FlowOverride` с CALL-инструкций → задать тело явно через
`FunctionManager.createFunction(...)`, исключив пул констант.

## 5. Порядок работы

### Шаг 1 — ПРОВЕРКА ГИПОТЕЗЫ (делай первым, это ключ ко всему)
Найди xref на строку **`4K_30`** (`0x006b8a50`) теперь, когда `.data` загружена.

- **Появились ссылки** → гипотеза подтверждена, `.data` и была недостающим звеном.
  Так и напиши, и дальше работай от них.
- **Ссылок по-прежнему нет** → гипотеза не подтвердилась. **Честно зафиксируй это** и
  переходи к шагу 3 (числовой поиск). Не подгоняй.

Для контроля сделай то же для `MF` (`0x006b8a71`) — заведомо используемое значение.
Если и на него ссылок нет, значит механизм адресации всё ещё не виден, и любые выводы
о «неиспользуемых» строках недействительны.

### Шаг 2 — Таблица режимов: `4K_30` против `4K_30_LOW`
Суффикс `_LOW` при том же разрешении и частоте почти наверняка означает **другой
битрейт**. Значит должна существовать таблица «режим → параметры кодирования», где эти
две записи отличаются, вероятно, ровно одним числом.

Найди структуру, в которой лежат обе строки. Выпиши **всю запись целиком** для
нескольких режимов (`4K_30`, `4K_30_LOW`, `FHD_30`, `VGA_240`) — построчно, по полям.
Даже если не поймёшь смысл каждого поля, сама таблица с адресами уже ценна.

### Шаг 3 — Числовой поиск (если шаг 2 не дал таблицы)
Ищи константы битрейта как LE32/LE16, **включая теперь `.data`**:
```
15000000 15500000 16000000 20000000 25000000 30000000 50000000 60000000 75000000
15000 15500 16000 20000 25000 30000 50000 60000 75000
```
Найденное **сверяй с измеренными** ~15.5 Мбит/с (FHD) и ~75 Мбит/с (4K).

### Шаг 4 — Профиль H.264
`profile_idc`: Baseline = **66**, Main = **77**, High = **100**. Ищи строки
`baseline`/`main`/`high`/`profile`/`CABAC`/`AVC`/`h264` и константу `66` рядом с
настройкой кодека. Константа `66` встречается повсеместно — засчитывай только со
ссылкой из релевантного кода.

### Шаг 5 — Лимит записи
Константы `1800` (сек), `1800000`/`30000` (мс). То же требование: только со ссылкой из
логики записи, иначе это шум.

.ROM.data      0x106ea800  116801     .log_save  0xc1c00000  2097152

почему часть логики может быть не в основном образе.
