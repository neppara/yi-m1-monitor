# Fable research — YI M1 RAW video / Magic Lantern feasibility

Дата: 2026-07-02
Автор: интернет-исследование (без доступа к камере и без нового анализа прошивки за пределами того, что уже лежит в `../research`).

## Зачем этот файл существует

В `../research/yi-m1-raw-video-feasibility.md` уже есть первичный анализ прошивки: платформа (ARM926/EV9x), карта секций, строки про RAW, план из 4 фаз. Эта папка — продолжение того же исследования, но через поиск в интернете: что уже пробовали другие люди на похожих камерах, и какие конкретные технические зацепки можно использовать, оставаясь в рамках "только софт, без пайки" (так пользователь ответил на уточняющий вопрос).

## Главный вывод этого захода

Предыдущий агент сфокусировался на офлайн-анализе прошивки (дизассемблирование, RAW-буферы, пропускная способность SD). В прошивке M1 нашлась строка `MTPClassDriver` вместе с Microsoft-овским OS-дескриптором MTP — маркер, которым Windows обычно определяет USB-устройство как **PTP/MTP** (Picture/Media Transfer Protocol), а не флешку. Это интересно, потому что PTP — ровно тот канал, через который независимые исследователи получили настоящее выполнение кода на Canon и Fujifilm без единой паяльной операции.

**Эта гипотеза проверена на реальной камере пользователя (2026-07-02) и не подтвердилась**: по USB-кабелю YI M1 всегда представляется обычной USB Mass Storage флешкой (подтверждено через `ioreg`/`diskutil` — карта памяти монтируется как обычный том), выбора режима на экране камеры нет, и в прошивке нет пользовательского переключателя USB-режима. Строка `MTPClassDriver`, скорее всего, мёртвый код от общего SDK, не подключённый к активному USB-дескриптору. Подробности и что это значит для дальнейшей работы — в [ptp-mtp-attack-surface.md](ptp-mtp-attack-surface.md).

Это не тупик для всего проекта — Wi-Fi HTTP API (уже описанный в `../research`, с готовой картой команд от проекта bullbin) остаётся живым и подтверждённым каналом управления, и именно туда сейчас имеет смысл вкладываться в первую очередь. См. [next-steps-safe-experiments.md](next-steps-safe-experiments.md).

## Закрытый вопрос: почему нельзя сменить видео-формат по Wi-Fi

Долгая многоходовая проверка (перебор параметров → дизассемблирование прошивки в Ghidra → поиск по сообществу и веб-архивам → декомпиляция официального APK через jadx) дала окончательный ответ: **официальное приложение YI Mirrorless никогда не реализовывало и не использовало ни одной команды удалённого управления видео** (`RCVideoFormatSet`, `VideoRecordingStart/Stop` и др. отсутствуют в декомпилированном коде приложения полностью). Строки и обработчики этих команд в прошивке — рабочий, но никем не используемый код (ни одним клиентом, включая официальный). Дальше в эту конкретную сторону копать бессмысленно. Подробности — в `live-testing-findings.md`, раздел 8.

- [final-assessment.md](final-assessment.md) — **итоговый ответ на изначальный вопрос**: что из "Magic Lantern для YI M1" реализуемо, а что нет, с доказательствами по каждому пункту. Начните отсюда.
- [live-testing-findings.md](live-testing-findings.md) — **журнал реальных экспериментов с камерой пользователя**: USB=Mass Storage (не PTP), реальный OEM камеры — Xacti, рабочий BLE-пейринг напрямую с компьютера, и полная карта того, какие Wi-Fi HTTP-команды реально работают (`RCISOSet`, `VideoRecordingStart/Stop`), а какие — 404 (`RCVideoFormatSet` и другие видео-сеттеры).

- [related-projects-and-community.md](related-projects-and-community.md) — что уже сделали другие люди конкретно с YI M1 и со смежным железом (bullbin, fujihack, форумы, находка про Xacti), и что из этого можно переиспользовать напрямую.
- [next-steps-safe-experiments.md](next-steps-safe-experiments.md) — конкретный пошаговый план экспериментов с реальной камерой, отсортированный по риску, начиная с абсолютно безопасных.
- [wifi-experiment-results/](wifi-experiment-results/) — сырые логи и захваченные кадры live view из реального прогона Wi-Fi HTTP API теста.
- [ghidra-disassembly-findings.md](ghidra-disassembly-findings.md) — первый заход в статический анализ прошивки через Ghidra: полная выверенная таблица из 45 HTTP-команд с адресами обработчиков (исправляет ошибочные адреса из `../research`), и ключевой вывод — видео-команды лежат в той же таблице с валидными обработчиками, что и рабочие команды, значит 404 приходит не оттуда.

## Приоритеты, которые пользователь задал для этого раунда

- Камера физически есть, можно тестировать (Wi-Fi API, DNG, режимы).
- Аппаратное вмешательство (пайка, UART/JTAG) — нет, только софт.
- Приоритет: реалистичные победы, а не RAW-moonshot или глубокая архивная работа по EV9x/Fujifilm-комьюнити ради самой архивности.
