# Карта памяти прошивки и недостающая секция `.data`

Дата: 2026-07-24. Статус: **извлечено из самой прошивки, проверено сверкой размеров.**

> ⚠️ **Если ты собираешься анализировать эту прошивку в Ghidra — начни отсюда.**
> Мы месяцами грузили 2 секции из 3 и из-за этого не могли построить ни одной
> перекрёстной ссылки на строки. См. раздел «Чем это нам стоило».

---

## 1. Где лежит карта

Подсекция **`firmware.bin.0.00004096`** (4096 байт, несжатая) — это таблица загрузки
секций. Записи содержат RAM-адрес, длину, флаги и ASCII-имя секции.

## 2. Секции с реальными данными — их ровно ТРИ

| Секция | RAM-адрес | Длина по таблице | Файл после распаковки | Размер файла |
|---|---|---|---|---|
| `.text` | `0x00002000` | 4 445 304 | `firmware.bin.0.00008192.decompressed` | 4 445 305 |
| `.rodata` | `0x0043f800` | 5 703 196 | `firmware.bin.0.03127296.decompressed` | 5 703 198 |
| **`.data`** | **`0xc09b0000`** | **339 536** | **`firmware.bin.0.07251968.decompressed`** | **339 542** |

Расхождения в 1, 2 и 6 байт — известный артефакт распаковщика (хвостовые нули от
добивки последнего флагового байта LZSS), тот же, что описан в
`rcvideoformatset-solved.md`. Соответствие однозначное.

**Загрузчик знает точные длины** и копирует ровно их, поэтому лишние хвостовые байты
никогда не читаются.

## 3. Полная карта (50 секций)

Данные несут только три выше; остальное — области RAM, буферы, стеки. В файле
прошивки их нет, но карта полезна для понимания устройства камеры.

### Что интересного видно
- **`.lens_cpu`** (`0xdf990000`, 3 МБ) — отдельная область памяти **процессора
  объектива**. Прямо связано с историей про электронно мёртвый китовый объектив
  (`lenType=""`, `lenVer="0.0"`).
- **`.xc_subcpu`** и **`.subcpu_OEM`** — субпроцессоры платформы Xacti («XC» = Xacti).
  То есть часть логики камеры вообще не в основном образе.
- **`.camadj` / `.camdef`** — калибровочные и определяющие данные камеры.
- **`.log_save`** (2 МБ) — область логов.
- **ITCM/DTCM** — быстрая внутрикристальная память для критичного кода.

## 4. Чем это нам стоило

Отсутствие `.data` в проекте Ghidra напрямую сорвало как минимум две задачи:

1. **`AGENT_TASK_06` (конфигурация энкодера) провалился.** Главный вывод отчёта был:
   «прямых 32-битных указателей на строки `4K_30` и `4K_30_LOW` не найдено, xref не
   строятся». Причина не в прошивке и не в исполнителе — таблицы указателей живут в
   `.data`, которой в проекте не было.

2. **Поиск ссылок на `MF-PEAK` дал ложный отрицательный.** Мы решили, что строка ни
   на что не ссылается. Контрольная проверка тогда же показала: на **заведомо
   рабочие** значения (`MF`, `S-AF`, `C-AF`) ссылок тоже нет. То есть метод молчал
   одинаково и для используемых, и для неиспользуемых строк — то есть не работал.

**Урок:** прежде чем делать вывод «на строку нет ссылок», проверь метод на строке,
про которую ТОЧНО известно, что она используется. Если контроль тоже молчит — молчит
метод, а не прошивка.

## 5. Как загружать правильно

```
1. Импорт .text:
   firmware.bin.0.00008192.decompressed
   -processor "ARM:LE:32:v5t"   (без суффикса :default)
   -loader BinaryLoader  -loader-baseAddr 0x00002000

2. В ТУ ЖЕ программу, через -postScript (Memory.createInitializedBlock):
   .rodata  <- firmware.bin.0.03127296.decompressed  @ 0x0043f800
   .data    <- firmware.bin.0.07251968.decompressed  @ 0xc09b0000
```

**Не использовать отдельные `-import`** — это создаст изолированные «программы» без
общих перекрёстных ссылок.

Санити-чек: строка `"RCVideoFormatSet"` должна лежать по `0x006b866c`.

# Отрицательный результат: параметров энкодера в этом образе НЕТ

Дата: 2026-07-24. Статус: **направление закрыто обоснованно, а не «не нашли».**

Сообщество годами просило поднять битрейт (bullbin issue #2: «хотя бы до 100 Мбит/с»,
DashCamTalk: «снять низкий битрейт и лимит 30 минут»). Мы искали, где это задаётся.
**В основном образе прошивки этого нет.** Ниже — чем это доказано.

## Что искали

Камера пишет H.264 **Constrained Baseline, level 41** (замерено `ffprobe` на реальных
файлах) — самый примитивный профиль, без B-кадров и CABAC. Переход на High profile дал
бы прирост качества **на том же битрейте**. Измеренные битрейты: FHD ~15.5 Мбит/с,
4K ~75 Мбит/с, 720p ~2.6 Мбит/с.

## Что нашли: таблица режимов по индексам

В `.data` по адресу **`0xc09c2ef8`** лежит массив из **13 указателей** на строки
режимов. Это полное перечисление, включая два режима, которые камера принимает по
HTTP, но не применяет:

| Индекс | Режим | | Индекс | Режим |
|---|---|---|---|---|
| 0 | `4K_30` | | 7 | `FHD_24` |
| 1 | `4K_24` | | 8 | `720P_60` |
| 2 | **`1920_24`** ← не применяется | | 9 | `720P_30` |
| 3 | **`2880_24`** ← не применяется | | 10 | `720P_24` |
| 4 | `2K_30` | | 11 | `VGA_240` |
| 5 | `FHD_60` | | 12 | `4K_30_LOW` |
| 6 | `FHD_30` | | | |

Массив найден вручную побайтово. **Ghidra на него ссылок не строит** — обращение идёт
через вычисляемое смещение. Проверено контролем: на заведомо используемое `MF`
(`0x006b8a71`) ссылок Ghidra тоже не показывает, хотя указатель на него лежит в
`.data` по `0xc09c1e58`. То есть молчит инструмент, а не прошивка.

## Чем доказано отсутствие параметров кодирования

Четыре независимые проверки, все отрицательные:

1. **Параллельного массива параметров в `.data` нет.** Если бы существовала таблица
   «индекс режима → битрейт/разрешение», она шла бы теми же 13 элементами. Искали
   последовательность ожидаемых ширин — не найдено. Более того, значения `2880`,
   `2160` и `640` в `.data` **не встречаются вообще**.

2. **В `.rodata` пар «ширина×высота» нет.** Проверены и 32-битные, и 16-битные пары
   для всех режимов. Показательно: **`2160` не встречается во всём блоке ни разу** —
   а без высоты кадра 4K никакая таблица видеорежимов существовать не может.

3. **`firmware.bin.1.ND1` (4.2 МБ, ранее не анализировался) — это шрифты и ресурсы
   интерфейса**, не прошивка субпроцессора. В начале блока:
   `MODEL_CODE=C59Y1  FONT_VERSION=Version 1.000  LANG=ENG`, дальше глифы.

4. **Скрытого четвёртого блоба в прошивке нет.** Секции `.ROM.text` (3 117 328),
   `.ROM.rodata` (4 124 556), `.ROM.data` (116 801) по размерам совпадают со **сжатыми**
   подсекциями (3 119 104 / 4 124 672 / 118 784). То есть `.ROM.*` — это те же три
   секции в упакованном виде, а не дополнительный код.

## Вывод

Параметры кодирования зашиты в **прошивке субпроцессора Xacti**. В карте памяти под
это есть отдельные области — `.xc_subcpu` (`0xdfc90000`, 3 МБ), `.subcpu_OEM`
(`0xdf590000`, 4 МБ) — но их содержимого **в `firmware.bin` нет**. Главный ARM, судя
по всему, лишь передаёт субпроцессору индекс режима из найденной таблицы.

**Практически: битрейт и профиль H.264 снаружи изменить нельзя, и перепрошивка
основного образа этого не решит.** Это не «мы не смогли найти» — этого здесь просто
нет, и теперь понятно, почему направление не поддавалось никому.

Что делать, если кто-то захочет продолжить: искать прошивку субпроцессора вне
`firmware.bin` (отдельный раздел флеш-памяти? загрузка по IPC при старте?) либо
трассировать на живом железе, что главный CPU отправляет субпроцессору при смене
режима. Оба пути требуют аппаратного доступа (UART/JTAG), который мы сознательно
исключили из проекта.

## Что это НЕ затрагивает

Всё уже работающее управляется через основной образ и никак не зависит от этого
тупика: смена видеоформата (включая 24p и 720p), слоу-моушен `VGA_240`, стабилизация,
звук, шумодав, громкость микрофона, все фото-настройки.
