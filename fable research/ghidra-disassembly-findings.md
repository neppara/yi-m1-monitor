# Ghidra-дизассемблирование прошивки — находки

Дата: 2026-07-02/03. Это первый реальный заход в статический анализ прошивки (Phase 0 из `../research/yi-m1-raw-video-feasibility.md`), выполненный полностью read-only против уже скачанного официального `firmware.bin` — камера в этом разделе не участвовала.

## Как настроено

- Ghidra 12.1.2 через `brew install ghidra` (тянет `openjdk@21` как зависимость).
- **Грабля**: `openjdk@21` — keg-only формула, `analyzeHeadless` без явного `JAVA_HOME` падает с "Unable to locate a Java Runtime". Решение — не системный симлинк (`sudo ln -sfn ...`), а просто явно передавать `JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home` при каждом вызове `analyzeHeadless`.
- Язык процессора: **`ARM:LE:32:v5t`** (ARM926EJ-S / ARMv5TE, little-endian) с компилятором `default`. Важно: `-processor` и `-cspec`/суффикс компилятора — разные флаги; `ARM:LE:32:v5t:default` одной строкой не работает, нужно `-processor "ARM:LE:32:v5t"` без суффикса.
- Работал через headless-режим (`analyzeHeadless`) с самого начала — GUI не использовался и не нужен для этой задачи.

## Ключевой вывод: 404 — не из-за отсутствия команды в таблице

**`RCVideoFormatSet`, `RCVASwitchSet`, `RCVAVolSet`, `RCVANoiseReduceSet`, `RCEisSwitchSet`, `VideoRecordingStart`, `VideoRecordingStop` — все лежат в ТОЙ ЖЕ таблице, тем же форматом записи, с такими же по виду валидными адресами обработчиков в `.text`, что и заведомо рабочие команды** (`RCISOSet`, `GetCameraStatus`, `RCImageAspect` и т.д.). Структурных отличий (флагов "включено/выключено", отдельного "черного" списка на уровне этой таблицы) не обнаружено.

Это меняет интерпретацию результата из `live-testing-findings.md` (раздел 6, перебор имён команд): раз таблица не объясняет разницу между рабочими и нерабочими командами, а `VideoRecordingStart`/`Stop` из этой же таблицы **точно работают** (подтверждено записанным видеофайлом), то 404 для `RCVideoFormatSet` и соседей возникает **не из-за отсутствия записи в этой таблице**, а из-за чего-то выше по стеку — вероятно, отдельного слоя HTTP/JSON-роутера, который решает, какие команды вообще долетают до диспетчера с этой таблицей.

## Продолжение (2026-07-05): найден сам диспетчер и путь к ошибке

Прямой поиск по сырым байтам указателя на таблицу (4-байтовое little-endian значение `ac 86 6b 00` = `0x6b86ac`) нашёл ровно одно вхождение — по адресу `0x1567d0`, внутри константного пула функции, которая начинается на `0x0015674c`. Автоанализ Ghidra ошибочно ограничил тело этой функции 40 байтами (из-за неверно определённых "non-returning" вызовов внутри — потребовалось вручную снять этот флаг и явно задать границы тела функции, см. "Как воспроизвести" ниже). После исправления декомпиляция дала полную логику.

### Диспетчер `FUN_0015674c` — что он реально делает

1. Проверяет флаг готовности (`*(struct+0x10) == 1`) — если нет, сразу `return -1`.
2. Парсит тело HTTP-запроса в список JSON key-value пар (через `FUN_001601f4`), получает количество пар `iVar2`. Если `< 1` — `return -1`.
3. Ищет среди пар ключ **длиной 7 байт, совпадающий строкой с `"command"`** (адрес строки `0x156978`, длина проверяется через параметр, переданный вызывающей функцией — всегда `7`).
4. Если "command" не нашёлся — уходит в отдельную ветку (не обязательно `-1`).
5. Если нашёлся — **копирует всю нашу таблицу из 45 команд (0x168 = 360 байт) с адреса `0x6b86ac` на стек** (`memcpy`), затем ищет среди скопированных 45 записей ту, чья строка **по длине и содержимому** совпадает со значением JSON-поля `"command"` в запросе.
6. При совпадении — берёт `handler_ptr` найденной записи и, судя по всему, вызывает его (это уже в коде вызывающей функции, не в этом диспетчере).
7. **Если совпадения нет — `return -1`.**

### Кто вызывает диспетчер и что делает с `-1`

Единственный вызывающий — `FUN_0014f47c` (сам HTTP-обработчик уровня выше). Ключевой фрагмент (декомпилировано):

```c
iVar5 = FUN_0015674c(iVar5 + 7, uVar3, *(undefined4 *)(uVar6 + 4));
if (iVar5 == -1) {
    FUN_00154c34();
    FUN_001510a0(1000, s_http_general_error_0014f69c, *(undefined4 *)(uVar6 + 4), 0);
    return uStack_14;
}
```

**Это и есть путь генерации ответа, который мы видим как `404 Not Found`** — строка `s_http_general_error` вызывается ровно тогда, когда диспетчер вернул `-1`. Цепочка полностью восстановлена: HTTP-запрос → `FUN_0014f47c` → `FUN_0015674c` (парсинг + поиск по таблице) → при неудаче поиска `-1` → `http_general_error`.

### Открытый вопрос: почему поиск не находит `RCVideoFormatSet`, хотя запись валидна

В цикле поиска по скопированной таблице замечена аномалия:

```c
do {
    iVar2 = aiStack_198[uVar6 * 2];         // table[uVar6].string_ptr
    if (puVar5[iVar7 * 4 + 4] == 3) {       // проверка типа JSON-значения
        ...сравнение длины и содержимого строки...
    }
    uVar6 = uVar6 + 1;
} while (uVar6 < 0x168);                     // <-- сравнение с 360, а не с 45 (0x2d)!
```

Граница цикла — `0x168` (360, это байтовый размер таблицы), а не `0x2d` (45, число реальных записей). Похоже на классическую C-ошибку `sizeof(array)` вместо `sizeof(array)/sizeof(array[0])` **в самой оригинальной прошивке**, не артефакт декомпиляции. Это означает, что цикл читает далеко за пределы скопированных 45 записей (в мусорные данные стека) на итерациях 45–359 — но поскольку `RCVideoFormatSet` находится в таблице на позиции ~38–39 (задолго до 45-й), сам этот выход за границы **не должен** мешать корректно найти именно её запись при простом линейном проходе 0…44.

Иными словами: **сама ошибка `sizeof` — реальная и подтверждённая находка, но она пока не объясняет однозначно, почему именно `RCVideoFormatSet` (а не `RCISOSet`, идущая раньше в этой же таблице) проваливает совпадение**. Кандидат на объяснение, ещё не проверенный: проверка `puVar5[iVar7*4+4] == 3` (тип JSON-значения) или то, как вычисляются границы значения (`puVar5[iVar7*4+6] - puVar5[iVar7*4+5]`) — возможно, зависит от длины/содержимого самого значения `"command":"RCVideoFormatSet"` (17 символов, длиннее большинства других команд) и где-то возникает off-by-one или переполнение промежуточного буфера при более длинных именах команд. Это не подтверждено — только гипотеза, требующая дальнейшей проверки (например, сравнить пошагово этот путь для `"RCISOSet"` (8 симв.) и `"RCVideoFormatSet"` (17 симв.) — не самая короткая команда в таблице, но одна из самых длинных: длиннее только `RCVANoiseReduceSet` (19), `RCShutterSpeedSet` (17, та же длина!), `RCChooseColorMode` (17, та же длина!) — при этом `RCChooseColorMode` физически не тестировалась в живых экспериментах, а `RCShutterSpeedSet` тоже не тестировалась (baseline-тест использовал только `RCISOSet`/`RCImageAspect`). **Стоило бы в следующий раз для этого протестировать вживую именно `RCShutterSpeedSet` — если она тоже не работает, дело в длине строки, а не в "видео"-специфике.**

## Как воспроизвести (проект живёт только в scratchpad сессии, пересоздаётся заново каждый раз)

Готового скрипта нет — шаги выполнялись вручную через `analyzeHeadless` с постскриптами на Java. Важные грабли, с которыми уже столкнулись и знаем решение:

1. `JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home` — обязательно указывать явно при каждом вызове `analyzeHeadless`, иначе "Unable to locate a Java Runtime".
2. Импорт `firmware.bin.0.00008192.decompressed` (`-processor "ARM:LE:32:v5t" -loader BinaryLoader -loader-baseAddr 0x00002000`), затем `firmware.bin.0.03127296.decompressed` добавляется в ТУ ЖЕ программу через `-postScript` с Java-скриптом, вызывающим `Memory.createInitializedBlock(".rodata", addr=0x0043f800, ...)` — НЕ через отдельный `-import` (иначе это будут две изолированные "программы" без общих xref).
3. После этого — обычный `-process <file> ` без `-noanalysis` (то есть без явного `-analyze`, такого флага не существует — анализ включён по умолчанию).
4. **Авто-анализ систематически неверно определяет границы некоторых функций** ("function body repair failed due to overlap" в логе) и ошибочно помечает некоторые вспомогательные функции как "non-returning", из-за чего декомпилятор обрезает тело вызывающей функции сразу после первого вызова такой "функции". Лечится так: `function.setNoReturn(false)` на конкретную функцию, ЛИБО (если это не помогает — декомпилятор использует свой собственный p-code анализ, независимый от флага на объекте Function) явно снять `FlowOverride` с каждой CALL-инструкции в нужном диапазоне (`instruction.setFlowOverride(FlowOverride.NONE)`), ЛИБО — самый надёжный способ — вручную задать тело функции явным `AddressSet` через `FunctionManager.createFunction(null, entry, body, SourceType.USER_DEFINED)`, предварительно исключив из диапазона байты встроенного пула констант (литералов), которые иначе дизассемблируются как мусорный код.
5. Диспетчер команд находится на `0x0015674c` (тело — `[0x15674c,0x1567af) + [0x1567e0,0x156977)`, между этими диапазонами — пул констант на 48 байт, включающий указатель на таблицу команд `0x6b86ac` по смещению `0x1567d0`).
6. Его единственный вызывающий — `0x0014f47c`, тело которого Ghidra определяет корректно само (380 байт, декомпилируется чисто).

## Продолжение (2026-07-06): поиск внешнего роутера-белого списка — отрицательный результат, и разбор кроп-функций сенсора

Ghidra-проект пересоздан с нуля по шагам выше (тот же scratch-каталог сессии, тот же `firmware.bin.0.00008192.decompressed` как единственная "программа" с добавленным `.rodata`-блоком). Автоанализ дал те же 24 790 функций, диспетчер на `0x0015674c` воспроизвёлся идентично прошлому разу (тело `508` байт после ручной фиксации границ и таблица `RCVideoFormatSet` подтверждена по тому же адресу `0x6b866c`) — воспроизводимость шагов "Как воспроизвести" подтверждена практически.

### Goal 1: внешнего белого списка команд НЕ существует — обоснованный отрицательный результат

Прослежена полная цепочка вызовов от точки приёма HTTP-соединения до диспетчера `0x0015674c`:

```
FUN_00025268 (event loop: accept/recv на сокете, единственный вызывающий FUN_0014e3ac)
  -> FUN_0014e3ac (per-connection обработчик, единственный вызывающий 0x14f47c)
       -> FUN_0014f47c (state-machine по *param_1, единственный вызывающий 0x15674c)
            -> FUN_0015674c (диспетчер по RC-таблице из 45 команд, уже описан выше)
```

Каждый переход подтверждён через `getReferencesTo()` — на каждом уровне **ровно один** вызывающий (не несколько альтернативных путей). Ключевые находки, закрывающие Goal 1:

1. **`FUN_0014e3ac`** — это НЕ второй уровень роутинга по имени команды, а фиксированная, безусловная последовательность вызовов нескольких обработчиков подряд (`FUN_0014f47c`, `FUN_00150064`, `FUN_00150aa0`, `FUN_00161ff4`, `FUN_0014dd5c`) — классический паттерн "у каждого модуля свой обработчик, вызываются все подряд, релевантный сам решает применяться ли". Соседние обработчики (`FUN_00150064` и др., декомпилированы) относятся к другим протоколам/командам этого же встроенного сервера (не HTTP RC-командам) — отдельная числовая таблица переходов на `0x150118` для другого набора функций, никак не связанная со строковыми именами команд.
2. **`FUN_0014f47c`** — сам по себе state-machine на числовом состоянии соединения (`*param_1`), НЕ на строке команды. Только когда состояние равно "тело запроса получено, метод POST" (`FUN_00163a64() == 2`, где `FUN_00163a64` — это просто `return *(состояние_соединения+8)`, т.е. чтение сохранённого HTTP-метода/этапа парсинга, без всякого сравнения строк), код передаёт управление в `FUN_0015674c(iVar5 + 7, uVar3, ...)` — единственная точка, где вообще выполняется сравнение строк с командами.
3. `FUN_00190130` (вычисляет длину, второй аргумент диспетчера) — это ровно `strlen()`, без какой-либо фильтрации.
4. Прямой побайтовый поиск 4-байтного little-endian указателя `0x6b86ac` (адрес начала RC-таблицы) по всему образу (`.text`+`.rodata`, ~10 МБ) дал **ровно одно** совпадение — то самое обращение внутри `0x0015674c`. Аналогично, единственная строка `RCVideoFormatSet` (`0x6b866c`) имеет **ровно один** xref — на саму себя из тела таблицы (`0x6b87ec`, слот `string_ptr` записи таблицы). Второй, независимой таблицы команд или второго строкового сравнения нигде в прошивке нет.

**Вывод по Goal 1 (уверенность высокая):** гипотеза про отдельный внешний роутер-белый список **не подтвердилась** и признаётся закрытой. Единственная проверка имени команды во всей цепочке от приёма TCP-соединения до вызова RC-обработчика — та самая проверка внутри `FUN_0015674c` по 45-записной таблице `0x6b86ac`. Значит, разница между `200` (`RCISOSet`, `VideoRecordingStart/Stop` и т.д.) и `404` (`RCVideoFormatSet`, `RCVASwitchSet`, `RCVAVolSet`, `RCVANoiseReduceSet`, `RCEisSwitchSet`, `StartMovieStream`) — это не эффект второго уровня фильтрации по имени. Это согласуется с финальным выводом из `live-testing-findings.md` (раздел 8, декомпиляция официального APK): эти команды просто никогда не были частью ни одного реального клиента и, по всей видимости, являются недоделанным/унаследованным кодом. Технически они **лежат в той самой единственной таблице и должны находиться диспетчером** — то, что часть из них всё равно даёт 404 на реальной камере, а не срабатывает, означает одно из двух (не различимо статическим анализом без дампа реальной прошивки с камеры): (a) в прошивке версии 3.2-int, установленной на камере пользователя, RC-таблица физически отличается от этого образа (эти записи вырезаны/заменены), либо (b) сам обработчик, найденный по адресу в таблице, при выполнении на реальном железе завершается с ошибкой на более ранней стадии (до генерации ответа), которая по какой-то причине маппится на тот же `http_general_error`/404 путь, а не на отдельный код ошибки — что стирает разницу между "команда не найдена" и "команда найдена, но обработчик сам вернул ошибку". Дальнейшее разграничение этих двух вариантов потребует **живого** теста (не статического анализа): например, JTAG/UART-доступ к реальной камере или сравнение реального дампа ROM камеры с этим образом побайтово.

### Goal 2: кроп-прямоугольник сенсора — частичный результат, конкретные числа не найдены, причина задокументирована

`ChangeSensorMode=` пересобран с нуля через побайтовый поиск строки (не по старому адресу-подсказке) — найден по адресу `0x00399afc`, с единственным xref из `FUN_00399964` (тело `436` байт, начало `0x00399964`) — то есть подсказка из прошлой сессии подтвердилась точно, без сдвига.

**Полная декомпиляция `FUN_00399964`** (диспетчер по числовому `param_1`, привязанный к общей структуре по указателю `DAT_00399ae8`):

- `param_1 == 1` или `2` — сброс `X_POS_FLG`/`X_POS`/`Y_POS_FLG`/`Y_POS` (смещения структуры `+0xa58/+0xa5c/+0xa60/+0xa68`) в `0xFFFFFFFF`/`0x100` (256) — похоже на "нет активного окна" / дефолт.
- `param_1 == 10` — записывает `X_POS_FLG = <значение из другого глобального указателя>`, `X_POS = puVar1[4]` (значение из отдельной структуры, тоже не статическая константа).
- `param_1 == 11` — аналогично для `Y_POS_FLG`/`Y_POS`.
- `param_1 == 999` (`0x3e7`) — специальная ветка: если `FUN_00394220()` (доп. проверка состояния) успешна, вызывает `FUN_00393d24()` — это и есть "применить" функция.
- Все остальные `param_1` (включая единственный найденный в прошивке вызов, см. ниже) — ветка `else`, которая: сбрасывает `X_POS_FLG=-1`, логирует `"ChangeSensorMode="` через `FUN_00190184`, затем **тоже** вызывает `FUN_00393d24()`.
- После любой ветки — печатает итоговые `X_POS_FLG/X_POS/Y_POS_FLG/Y_POS` через debug-print (`FUN_001902ac` + `FUN_0010c1ec`), это и есть источник строк `X_POS_FLG=`/`X_POS=`/`Y_POS_FLG=`/`Y_POS=`, увиденных в прошлой сессии.

**`FUN_00393d24` (624 байта, полностью декомпилирован) — это НЕ сеттер кропа по таблице, а живой поисковый алгоритм автофокуса.** Это подтверждает и усиливает (а не просто повторяет) предположение из прошлой сессии. Функция крутит цикл, на каждой итерации записывая **временные, маленькие смещения окна сканирования** (`iVar6 = iVar7*8`, `iVar4 = iVar12*2+0x74`/`0x18c` — шаги порядка единиц-десятков пикселей, не размеры кадра) в те же поля `X_POS/Y_POS/X_POS_FLG/Y_POS_FLG`, вызывает `FUN_00393940`+`FUN_00393c90` (примитивы чтения контраста/резкости с сенсора в этом окне) и итеративно ищет пик по разнице показаний (`(uint)(puVar1[4] + puVar1[2]) >> 1) - ...` — классический бинарный/градиентный поиск фокуса). Итоговый прямоугольник, который остаётся в структуре после этой функции, — это положение окна автофокуса на момент завершения поиска, **не описание кроп-рамки видео-кадра**.

**Единственный вызов `FUN_00399964` во всей прошивке** найден не через xref-таблицу Ghidra (авто-анализ его не увидел — классическая проблема невидимого `BL` внутри неверно размеченного блока), а через побайтовый скан всех `BL`-инструкций ARM в `.text` (26 МБ инструкций проверено вручную декодированием `cond|101L|imm24`): ровно один `BL 0x00399964` найден на `0x0010eb34`, внутри огромного (900+ веток) числового диспетчера `FUN_0010dfa0`/окружающих таблиц перехода (`0x10dfa0`-`0x10edcc`+), который относится к **общей системе применения настроек камеры по числовому ID** (`uVar1 < 900` идёт в `SupervisorCall`, т.е. это диспетчер синхронных вызовов ядра/RTOS, не HTTP-специфичный). В блоке-обёртке вокруг этого `BL` (`0x10eb10-0x10eb3c`) нет свежей загрузки `r0` непосредственно перед вызовом (в отличие от соседних кейсов, которые явно делают `mov r0,r6`) — то есть `param_1` для этого единственного вызова — не литеральная видео-режимная константа, а унаследованное значение регистра из предыдущих вызовов-обёрток (`FUN_000fe908`, `FUN_0010d92c` — эти лишь читают/переключают битовый флаг блокировки, возвращают 0/1). Практически это означает, что реальный код почти наверняка вызывает `FUN_00399964` с `param_1 == 0` в этой точке — что не совпадает ни с одним из явно обработанных случаев (1/2/10/11/999/3) и попадает в тот же `else`, что и `param_1 == 999`: то есть это универсальная точка "пересчитать текущее положение АФ-окна", а не "установить кроп для режима X".

**Проверена и отвергнута альтернативная гипотеза о `MOV_Set_WorkArea` (`FUN_00323ff0`, 2320 байт, декомпилирован полностью).** Эта функция управляет размещением VRAM/DRAM-буферов ISP-конвейера (адреса кадровых буферов вида `0xc0000000`-диапазон, смещения `+0x30000`/`+0x40000` и т.д.) для разных кодек-режимов (`*param_1` = 0..9), а НЕ геометрией кроп-окна сенсора — путаница исключена явным чтением кода: `param_1[0x28]`/`[0x29]` (ширина/высота) читаются как **входные параметры от вызывающего**, а не как захардкоженные в этой функции значения. Оба вызывающих (`FUN_0005d374`, `FUN_0009d4e8`) — тонкие обёртки, вызываемые из **14 разных мест** в прошивке (не только видео — общий механизм смены режима захвата и для фото, и для видео), что делает выделение "именно видео-режимных" числовых констант отсюда практически невозможным без динамической трассировки регистров на реальном железе.

**Проверена и отвергнута гипотеза про табличные константы разрешений.** Побайтовый поиск литералов `1920`, `5184`, `3888`, `3840`, `2160`, `1080` и др. по всему образу нашёл кластер `1920`/`5184`/`3888`/`1440`/`3456` рядом друг с другом на `0x0052f500`-`0x0052f680`, но сразу за этим блоком идут читаемые ASCII-строки `MISC`, `AUT`, `PRINT`, `MRK` — это шаблон/константы EXIF/DPOF-тегов для генерации превью в DNG/JPEG (согласуется с ранее подтверждённым `software: ASDK-00142` в реальном DNG-файле), не таблица видео-режимов. На эту область нет ни одного xref из кода — похоже на статический блоб, копируемый как есть в заголовки файлов, а не читаемый программно по индексу режима.

**Итоговый вывод по Goal 2 (уверенность высокая для "нет статической таблицы", низкая/отсутствует для "точные числа кропа"):** в этой прошивке нет статической таблицы вида `{video_mode → x,y,w,h}`, которую можно было бы просто прочитать из ROM. Кроп-геометрия для каждого видео-режима, судя по всему, **вычисляется во время выполнения** через код, который отвечает одновременно и за автофокус, и за раскладку VRAM-буферов ISP, используя оперативные (не статические) значения сенсора/калибровки, которые физически не присутствуют в статическом образе прошивки (только адреса RAM-структур вида `0xc1xxxxxx`, куда что-то пишется в рантайме). Получить реальные числа для 4K/FHD/2K потребует **динамического** анализа (JTAG-отладка живой камеры, дамп памяти во время работы, либо логирование фактических значений `X_POS`/`Y_POS`/`X_POS_FLG`/`Y_POS_FLG` через существующие debug-print вызовы, если в прошивке есть включаемый debug-UART) — вне рамок статического Ghidra-анализа без физического доступа к плате. Комментарий в `main_window.py`/`ARCHITECTURE.md` **не обновлён** — по существу нечего туда вписать взамен текущей честной формулировки "не измерено"; сама формулировка остаётся корректной и точной.
