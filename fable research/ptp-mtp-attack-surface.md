# PTP/MTP как точка входа — гипотеза проверена, опровергнута для стандартного режима

## ОБНОВЛЕНИЕ (2026-07-02, проверено на реальной камере)

Гипотеза ниже была проверена на живой камере пользователя (macOS, `ioreg -p IOUSB`, диагностика подключения по USB-кабелю без выбора режима на экране камеры — выбора и не было предложено). Результат:

- `bInterfaceClass = 8` (USB Mass Storage), `bInterfaceSubClass = 6` (SCSI transparent command set), `bInterfaceProtocol = 0x50` (Bulk-Only Transport).
- macOS подключил интерфейс через штатный `IOUSBMassStorageInterfaceNub`, карта памяти камеры примонтировалась как обычный том (`/Volumes/Untitled`, NTFS, 63.8 ГБ).
- В прошивке нет строк вида `USB_MODE`/переключателя режима USB в пользовательском меню — единственная околоусбшная настройка, `usbdesc_composite=0x%x`, выглядит как инженерный/отладочный параметр IPL-загрузчика (судя по соседним строкам `usbssphy_*`, `usbutmi_ctl` — это регистры USB3 PHY, печатаются, скорее всего, только по UART на debug-сборке), а не пункт меню, доступный без UART.

**Вывод: в штатном режиме подключения по USB-кабелю YI M1 — это просто флешка, а не PTP/MTP-устройство.** Строка `MTPClassDriver` в прошивке (см. ниже) почти наверняка мёртвый код из общего SDK/RTOS, используемого другими продуктами на этой платформе, но не подключённый к активному USB-дескриптору данной камеры. Без UART-доступа (что вне рамок задачи — только софт) переключить это не получится.

Это закрывает вектор "USB PTP как у Check Point/fujihack" как нереалистичный для этой камеры *в её текущем виде*. Три прецедента ниже остаются ценными как методология (см. `related-projects-and-community.md`), но не как прямая точка входа через штатный USB. Актуальный приоритет — Wi-Fi HTTP API (раздел 2 в `next-steps-safe-experiments.md`), который остаётся живым и подтверждённым каналом.

## Факт из прошивки (исходная гипотеза, для истории)

В файле `../research/YI-M1-firmware-3.2-int/3.2-int/firmware.bin.0.00008192.decompressed`, по смещению `0x3074f4`, лежит блок:

```
Windows\x00MTPClassDriver\x00\x000\xc8Y\xc1Windows/6.0.\x00\x00\x00\x00Windows/6.1.\x00\x00\x00\x00
```

Это не случайная строка. Это стандартный **Microsoft OS String Descriptor** для MTP-устройств (тот самый механизм, которым USB-девайс говорит Windows: "не грузи меня как флешку, я — MTP/PTP-устройство, грузи WPD-стек"). Наличие этого дескриптора означает, что прошивка M1 содержит полноценный **MTP-респондер** (MTP — надмножество PTP, Picture Transfer Protocol, ISO 15740).

Это отдельный канал от уже задокументированного в `../research` Wi-Fi HTTP API (`192.168.0.10`, команды типа `RCVideoFormatSet`). HTTP API, судя по всему, самодельный протокол YI поверх Wi-Fi. MTP/PTP — это то, что включается по USB-кабелю (обычно так камера отдаёт файлы на компьютер / принимает команды тетеринга в приложениях типа Lightroom/Capture One).

**Что не подтверждено:** не проверено вживую, действительно ли камера в реальном режиме подключения по USB представляется компьютеру как PTP/MTP-устройство (а не просто как USB Mass Storage флешка с картой памяти). Строка в прошивке доказывает, что код респондера скомпилирован и присутствует, но не доказывает, что он активен во всех режимах. Это первое, что стоит проверить руками (см. `next-steps-safe-experiments.md`).

## Почему это важно: три прецедента

### 1. Canon EOS 80D — Check Point Research, DEF CON 27 (2019)

Check Point нашли пять переполнений буфера в реализации PTP у Canon:

| CVE | Функция | Тип |
|---|---|---|
| CVE-2019-5994 | `SendObjectInfo` | переполнение буфера при разборе Unicode-имени файла |
| CVE-2019-5998 | `NotifyBtStatus` | stack overflow в обработчике статуса Bluetooth |
| CVE-2019-5999 | `BLERequest` | heap overflow в Bluetooth-команде |
| CVE-2019-6000 | `SendHostInfo` | stack overflow из-за небезопасного логирования уже провалидированных данных |
| CVE-2019-6001 | `SetAdapterBatteryReport` | stack overflow в отчёте о батарее адаптера |

Через CVE-2019-6000 (доступную по Wi-Fi) они получили полноценное удалённое выполнение кода на EOS 80D и продемонстрировали ransomware поверх PTP — вообще без физического доступа к камере. Инструменты: Magic Lantern'овский ROM-дампер (!) для снятия памяти, IDA Pro для дизассемблирования, `ptpy` (Python) для конструирования пакетов, кастомный отладчик "Scout", загруженный через сам эксплойт.

Ключевая цитата из их вывода: протокол PTP стандартизирован и используется другими производителями, "мы полагаем, что похожие уязвимости можно найти в реализациях PTP и у других вендоров". Это прямое приглашение проверить то же самое на YI M1.

Источник: [Check Point Research — Say Cheese: Ransomware-ing a DSLR Camera](https://research.checkpoint.com/2019/say-cheese-ransomware-ing-a-dslr-camera/)

### 2. Fujifilm — проект fujihack (Daniel Cook, он же petabyt)

Автор получил кастомное выполнение кода на нескольких камерах Fujifilm (XF1, X-A2 и др.) через патч "PTP/USB debugger", который добавляет прошивке возможность читать/писать/исполнять память через PTP-канал. Метод:

1. Снял дамп памяти (~200 КБ, позже до 256 МБ) через уязвимость/недокументированную возможность.
2. Методом brute-force поиска по RAM нашёл таблицу функций-обработчиков PTP-команд (без исходников, без символов отладки — только по паттернам).
3. Перехватил (hijack) эти обработчики, подставив свой код.
4. В итоге получил произвольное чтение/запись/исполнение прямо через штатный USB-кабель, без прошивки нового образа целиком.

Автор отдельно отметил: в прошивке много несжатых участков (около 60% файла обновления) — именно туда проще всего внедрять патч-код, сжатые участки редактировать неудобно.

Источники:
- [danielc.dev — Hacking the Fujifilm Digital Cameras](https://danielc.dev/blog/hacking-the-fujifilm-digital-cameras/)
- [danielc.dev — What I learned after a year of reverse engineering](https://danielc.dev/blog/what-i-learned-after-a-year-of-reverse-engineering/)
- [danielc.dev — 2 Years of Fujihack](https://danielc.dev/blog/2-years-of-fujihack/)
- [github.com/fujihack/fujihack](https://github.com/fujihack/fujihack)

### 3. Canon + Magic Lantern — сама установка ML идёт через PTP

Тот же автор написал `mlinstall` — инструмент установки Magic Lantern, который использует недокументированную PTP-команду Canon (opcode `0x9052`, "eventproc") для удалённого вызова `EnableBootDisk` и записи boot-флага на карту — то есть даже штатная установка Magic Lantern на Canon делается через PTP-канал по USB, а не физическими манипуляциями с картой в кардридере.

Источник: [github.com/petabyt/mlinstall](https://github.com/petabyt/mlinstall)

## Вывод для YI M1

Три независимых прецедента (Canon x2, Fujifilm) показывают одну и ту же модель: **PTP/MTP-канал по USB — самый частый способ получить реальный контроль над камерой без вскрытия корпуса**. Раз в прошивке M1 есть MTP-респондер, это должно стать приоритетной точкой входа для дальнейшей практической работы — приоритетнее, чем слепое дизассемблирование ARM926-кода ради поиска RAW-буфера.

Практический план проверки — в [next-steps-safe-experiments.md](next-steps-safe-experiments.md), раздел 1.

## Инструменты для работы с PTP (все — софт, никакого железа)

- `libgphoto2` / `gphoto2` CLI — если камера неизвестна библиотеке, она всё равно опрашивается как "generic PTP" и покажет `GetDeviceInfo` (список поддерживаемых операций). Ставится через `brew install libgphoto2 gphoto2` на macOS.
- [`ptpy`](https://pypi.org/project/ptpy/) — чистый Python, использовался Check Point для конструирования PTP-пакетов.
- [`petabyt/libpict`](https://github.com/petabyt/libpict) — C-библиотека PTP-клиента того же автора, что и fujihack; умеет `ptp_get_device_info()`, отдаёт ответы в JSON, есть Lua-биндинги.
- [`petabyt/vcam`](https://github.com/petabyt/vcam) — переимплементация проприетарных MTP-респондеров для чёрного тестирования; полезно как референс методологии, не как инструмент против самой камеры.
