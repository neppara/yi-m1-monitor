# Код-ревью обоих приложений (2026-07-24)

Полный проход по накопленному коду iOS и macOS на предмет стабильности и опасных мест.
Объём: ~9 000 строк (macOS 4 189, iOS 6 189 без тестов).

Всё найденное ниже **исправлено и проверено**; в конце — список того, что проверено и
признано корректным (чтобы не перепроверять заново).

---

## КРИТИЧНОЕ

### 1. iOS: скачивание видео убивало приложение (OOM)

`HTTPClient.performDownload` собирал **весь файл в память**:

```swift
var data = Data()
if total > 0 { data.reserveCapacity(total) }   // ← резервирует Content-Length целиком
for try await byte in asyncBytes {
    data.append(byte)                           // ← побайтово
}
```

а `downloadFile` затем писал это на диск одним куском.

Клип с этой камеры доходит до **4 ГБ** (потолок FAT32). Что происходило:

| Файл | Резервируется в RAM | Итераций append |
|---|---|---|
| 100 МБ | 105 МБ | 105 млн |
| 1 ГБ | 1.05 ГБ | 1.05 млрд |
| **4 ГБ** | **4.29 ГБ** | **4.29 млрд** |

iPhone убивает обычный процесс (jetsam) примерно на 1.4–2 ГБ, то есть **скачивание
большого видео гарантированно роняло приложение** — причём до того, как файл вообще
начал бы писаться. Плюс побайтовый `append` по AsyncSequence: миллиарды итераций.

**Исправлено:** добавлен `download(_:to:)`, который стримит **прямо на диск** через
`FileHandle` чанками по 64 КБ. Пиковая память постоянна независимо от размера файла.
Для загрузок в память (превью/миниатюры) введён потолок
`maxInMemoryDownloadBytes = 32 МБ`. При ошибке недописанный файл удаляется.

### 2. macOS: незадренированные соединения рвали сессию (4 места)

Тот же класс, что баг #18 (превью видео). Камера обслуживает **одного клиента**;
если вернуть в пул **недочитанный** ответ, пока камера ещё пишет, следующий запрос
получает залипший сокет → падают `GetCameraStatus` → детектор «камера исчезла»
отключает приложение.

Найдено четыре точки с `release_conn()` без дренирования:

| Место | Когда срабатывает |
|---|---|
| `_do_download`, ошибка записи | диск полон, нет прав — файл качается, запись падает |
| `_do_download`, HTTP ≠ 200 | прочитано 200 байт превью, **остаток тела брошен** |
| `_download_preview_with_progress`, HTTP ≠ 200 | тело не прочитано вовсе |
| `_download_preview_with_progress`, `finally` | прерванное чтение — **после каждого снимка** |

Последнее опаснее всего: фото-ревью выполняется при каждом спуске затвора.

**Исправлено:** общий хелпер `_drain_and_release()` — дренирует остаток, потом
отпускает соединение; устойчив к `None` и к битому объекту ответа. Все четыре места
переведены на него, голых `release_conn()` в коде не осталось.

### 3. macOS: детектор «камера исчезла» не срабатывал для залипшей камеры

Статус-поллинг проверял `status == 200`:

```python
status, body = self._send({"command": "GetCameraStatus"})
if status == 200:
    consecutive_status_failures = 0      # ← сброс даже на теле-ошибке
```

Камера сообщает сбои как **HTTP 200 + `{"code":<err>}`** — это давно известный факт
проекта, ради него и написан `is_camera_success`. Но именно в поллинге он не
использовался. Следствие: камера, которая отвечает, но **не работает** (ровно то
состояние, в которое её загоняли пункты выше), считалась здоровой, и детектор
потери связи не срабатывал **никогда**.

**Исправлено:** поллинг переведён на `is_camera_success`.

## СРЕДНЕЕ

### 4. Частично скачанный файл оставался на диске

При обрыве записи файл оставался — в Finder выглядит валидным, а не открывается.
**Исправлено** на обеих платформах: битый файл удаляется, ошибка возвращается наверх.

## Проверено и признано корректным

Чтобы не перепроверять по кругу — здесь то, что смотрел и где проблем нет.

| Область | Вывод |
|---|---|
| Границы массивов в реассемблинге UDP | защищено на обеих платформах, лимит 1024 пакета, паритет |
| Деления на ноль | все под guard (`if elapsed > 0`, `if expected > 0 else 0`) |
| Force unwrap / индексы (Swift) | практически отсутствуют; `credParts[0..1]` под `guard count == 2` |
| Таймауты HTTP | есть у всех запросов на обеих платформах |
| Сброс счётчиков при переподключении | симметричен (приёмник и сессия сбрасываются согласованно) |
| Отмена задач при disconnect | `connectTask`/`liveViewTask`/`statusPollTask`/`reviewClearTask`/`autoRestartTask` отменяются |
| Fire-and-forget задачи iOS | с `[weak self]`; без него — только те, что не трогают `self` |
| Сериализация запросов | соблюдена: камера обслуживает один запрос за раз, скачивание держит очередь |
| Кэши миниатюр | живут внутри диалога/представления, умирают вместе с ним — не утечка |
| Типы счётчиков (Swift) | `Int`, не `UInt` — вычитание не роняет рантайм |

## Замеченное, но НЕ исправленное (осознанно)

1. **`_do_shoot_and_review` использует `status == 200` для `GetFileList`.** Деградирует
   безопасно: тело-ошибка не распарсится в список, цикл просто продолжит попытки. Худший
   случай — 8 секунд впустую вместо мгновенной ошибки. Трогать не стал, чтобы не менять
   поведение горячего пути ради косметики.
2. **Долгое скачивание подмораживает live view на macOS** — следствие однопоточной
   модели, известное и задокументированное. Переделка архитектуры ради этого не
   оправдана.
3. **iOS `fetchFileData` не пишет на диск** — он и не должен, это путь для превью, и
   теперь он ограничен 32 МБ.

## Итог

Найдено **три критичных** проблемы и одна средняя. Общая черта у большинства: они
проявляются только на **путях ошибок и на больших файлах** — то есть там, куда обычное
тестирование не заходит. Отсюда и то, что баг с превью видео нашёлся раньше остальных:
он был единственным, который срабатывал при нормальном использовании.

Самая опасная — iOS OOM: она не портила данные, но гарантированно роняла приложение на
реальном сценарии (скачать снятое видео на телефон).

Проверка после правок: 53 теста iOS зелёные, оба приложения собираются, macOS-фиксы
прогнаны смоук-тестом на реальных ответах камеры из логов.
