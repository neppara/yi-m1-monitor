# Живое тестирование на реальной камере — журнал находок

Дата: 2026-07-02. Всё ниже — результаты реальных экспериментов с камерой пользователя (не из интернета), выполненных в рамках этого исследования. Полные сырые данные экспериментов с Wi-Fi API лежат в [wifi-experiment-results/](wifi-experiment-results/).

## 1. USB: Mass Storage, не PTP/MTP (см. также `ptp-mtp-attack-surface.md`)

Проверено через `ioreg -p IOUSB`: `bInterfaceClass=8` (Mass Storage), `bInterfaceSubClass=6`, `bInterfaceProtocol=0x50` (Bulk-Only Transport). Карта монтируется как обычный том. Гипотеза про PTP/MTP-канал по USB (из строки `MTPClassDriver` в прошивке) не подтвердилась для штатного подключения кабелем. Выключенная камера вообще не видна по USB (не поднимает контроллер в любом режиме).

## 2. Реальный OEM — Xacti Corporation

BLE-характеристики стандартного GATT-профиля отдают:
- `manufacturer` = **Xacti**
- `model` = **ASDK00**

Xacti — японский производитель камер/камкордеров (бывшее фото-видео подразделение Sanyo). Это объясняет строку `C:/XC_ODM/sdk/...` из прошивки ("XC" = Xacti) и означает, что YI M1 построена на аппаратной платформе/SDK Xacti, а не на собственной разработке Xiaoyi с нуля. См. подробности и что это меняет для дальнейшего поиска — в `related-projects-and-community.md`.

## 3. BLE-пейринг с камерой напрямую с компьютера — работает, с оговорками

Библиотека `bullbin/xiaoyi_m1_re_liveview` (`prot_ble/ble_keyhack.py`) в теории позволяет получить SSID/пароль Wi-Fi камеры напрямую по Bluetooth, без официального приложения на телефоне. На практике потребовалась доработка (все патчи сохранены в `../../` рабочей копии репозитория в scratchpad сессии, не в этой папке — при желании воспроизвести, см. ниже):

- На macOS процесс, вызывающий CoreBluetooth без прав на Bluetooth в Privacy & Security, не получает диалог с ошибкой — **система жёстко убивает процесс (`SIGABRT`)**. Решение: запускать только из подписанного приложения-хоста (обычный Terminal.app), которому macOS может выдать разрешение и реально его спросит.
- `BleakScanner.discover()` в отдельном вызове, а затем `BleakClient(address)` в отдельном `asyncio.run()` — ненадёжно на macOS (device not found / timeout), потому что каждый вызов создаёт новый `CBCentralManager`, который не обязательно видит устройство, найденное предыдущим менеджером. Решение: сканировать и подключаться в одной сессии, используя объект найденного устройства напрямую.
- Фильтрация по `service_uuids` в `BleakScanner` на этой версии macOS/bleak оказалась ненадёжной — в одном прогоне под видом "лучшего кандидата" вернулся случайно оказавшийся рядом iPhone. Решение: сканировать без фильтра и вручную проверять, что `UUID_SERVICE_M1` (`41106dd9-25ad-477b-a884-5038b6de4649`) реально присутствует в `advertisement_data.service_uuids` найденного устройства, а не доверять фильтру сканера.
- Прошивка камеры не отдаёт стандартную GATT-характеристику "Device Name" (`00002a00-...`) — `retrieve_info()` из библиотеки на этом падает, хотя это поле нигде дальше не используется. Решение: делать необязательные стандартные поля (name/manufacturer/model) устойчивыми к ошибке, полагаться только на кастомную характеристику Firmware Info камеры.

После этих правок пейринг прошёл успешно: получены `SSID=YI_M1_cc7abd`, `Pass=<8-значный, меняется каждую сессию>`. Протокол пейринга подтверждён рабочим (версия протокола BLE = 1, прошивка `3.2-int`, вариант `M1INT`).

## 4. Wi-Fi HTTP API — что реально работает, а что нет

Полный лог: [wifi-experiment-results/run_20260702_232157/log.txt](wifi-experiment-results/run_20260702_232157/log.txt).

| Команда | Результат | Комментарий |
| --- | --- | --- |
| `GetCameraStatus` | `200`, реальные данные | батарея 75%, 691 свободных фото |
| `RCStartRemoteCtl` | `200` | сессия ПДУ стартует |
| `RCISOSet {"ISO":"Auto"}` | `200`, **и реально применилось** | подтверждено по метаданным live view: `ISOSetting` изменился с `"200"` на `"Auto"` между 1-м и 700-м кадром |
| `RCVideoFormatSet` (варианты ключа `VideoFormat`/`Value`/`Mode`, все значения `4K_30`/`4K_24`/`4K_30_LOW`) | **404 Not Found** (HTML, не JSON) | HTTP-сервер вообще не знает такой команды — не «неверный параметр», а полностью нераспознанная строка команды на уровне роутинга |
| `RCVASwitchSet`, `RCEisSwitchSet`, `RCVANoiseReduceSet` (без параметров, просто проверка существования) | **404** | та же история — команды из строк прошивки не зарегистрированы в HTTP-роутере этой сборки |
| `VideoRecordingStart` | **`200`** | похоже, реально сработало — команда распознана и принята |
| `VideoRecordingStop` | **`200`** | отправлено через ~0.6 с после Start, для безопасности при неконтролируемом прогоне |
| `RCStopRemoteCtl` | `200` | чистое завершение сессии |

### Что это значит

1. **HTTP-командный роутер камеры строже, чем список строк из дизассемблированной прошивки.** То, что строка `RCVideoFormatSet` встречается в таблице обработчиков внутри бинарника (см. `../research/yi-m1-raw-video-feasibility.md`), не гарантирует, что она подключена к тому же HTTP-серверу, который обрабатывает `RCStartRemoteCtl`/`RCISOSet` и т.д. Возможно, эта команда: (а) относится к другому, не-Wi-Fi интерфейсу (например, только USB-тетерингу), (б) убрана/отключена в актуальной прошивке 3.2-int, либо (в) требует другого, ещё не найденного имени команды.
2. **`VideoRecordingStart`/`VideoRecordingStop` — реально работающая пара команд.** Это уже само по себе полезно: можно удалённо стартовать/останавливать запись видео по Wi-Fi, независимо от того, можно ли удалённо менять формат/разрешение. Стоит проверить карту камеры на предмет короткого видеофайла с меткой времени around 23:22:24–23:22:26 (2026-07-02) — если он есть, это будет прямым подтверждением, что запись реально включилась, а не просто вернула "OK" без эффекта.
3. **В метаданных live view (JSON, который камера сама транслирует по UDP) есть поле `VideoFormat` со значением `FHD_30`** — то есть камера в момент теста действительно была в режиме Video Live View (пользователь заранее зажал REC), и это поле — рабочий, живой источник текущего видео-режима, даже если писать в него через `RCVideoFormatSet` не вышло. Там же — `VASwitch`, `VAVol`, `VANR`, `VideoEis`, которые совпадают по названию с командами `RCVASwitchSet`/`RCVAVolSet`/`RCVANoiseReduceSet`/`RCEisSwitchSet` из прошивки: то есть **чтение** этих параметров работает (через поток метаданных), а вот их **запись** через одноимённые HTTP-команды — нет (404).

### Подтверждено физически: VideoRecordingStart/Stop реально записали видео

Пользователь нашёл на карте камеры (`/Volumes/Untitled/DCIM/100YICAM/P7020465.MP4`, 200 288 байт, метка времени 22:23) секундный ролик с чёрным экраном (крышка объектива была закрыта — ожидаемо). Проверено через `ffprobe`:

```
Видео: H.264, 1920x1080, 30000/1001 fps (~29.97), битрейт ~427 кбит/с
Аудио: AAC, ~125 кбит/с
Длительность: 1.001 с
```

Это **точно совпадает** с `VideoFormat=FHD_30`, который отдавала камера в метаданных live view. Полное железное подтверждение: `VideoRecordingStart`/`VideoRecordingStop` по Wi-Fi реально запускают и останавливают настоящую запись на камере — рабочий, воспроизводимый канал удалённого управления видеозаписью, без каких-либо физических действий с камерой.

(Метка времени файла 22:23:15 против ожидаемых по логу 23:22:24–23:22:26 — расхождение ровно около часа, похоже на разницу часовых поясов между камерой и Mac, а не на несовпадение событий.)

## 7. `StartMovieStream`/`PauseMovieStream`/`ResumeMovieStream`/`StopMovieStream` — проверено вживую (2026-07-06)

Из таблицы 45 обработчиков (`ghidra-disassembly-findings.md`) эта четвёрка команд никогда раньше не отправлялась камере — только упоминалась как "не встречается в официальном приложении". Проверено через `yi-m1-remote-control/probe_movie_stream.py` (обычная сессия ПДУ + голая отправка каждой команды подряд + подсчёт пакетов на UDP live-view порту 54321 до/после каждой):

| Команда | HTTP-статус | Эффект на UDP live-view поток |
| --- | --- | --- |
| `StartMovieStream` | **404** (обычная HTML-страница not found) | — |
| `PauseMovieStream` | **200** `{"code":200}` | нет — поток идёт с той же скоростью (~3900-3960 пакетов/3с) |
| `ResumeMovieStream` | **200** `{"code":200}` | нет |
| `StopMovieStream` | **200** `{"code":200}` | нет |

Это первый случай во всём исследовании, когда команда из "непроверенных" реально прошла HTTP-роутер (200), а не 404 — до этого весь класс "видео"-команд (`RCVideoFormatSet`, `RCVASwitchSet`, `RCEisSwitchSet`, `RCVANoiseReduceSet`) давал чистый 404. Асимметрия интересна сама по себе: `StartMovieStream` не прошёл, а `Pause`/`Resume`/`Stop` того же семейства — прошли. По уже известной методологической оговорке (см. раздел про `RCVideoFormatSet` выше) 404 на голую команду не доказывает, что она не подключена — она может требовать обязательный параметр, который не был угадан. Но раз соседние команды того же семейства принимаются без параметров (как `RCDoShooting`/`VideoRecordingStart`), это не выглядит как основная причина именно для `StartMovieStream`.

**Гипотеза "MovieStream относится не к live view, а к активной записи" — проверена и не подтвердилась.** Два прогона через `probe_movie_stream_pause_recording.py` (Start → 2с → Pause → 3с ожидания → Resume → 2с → Stop) и `probe_video_duration_baseline.py` (тот же тайминг, без Pause/Resume вообще):

| Прогон | Часы (Start→Stop) | Реальная длина файла |
| --- | --- | --- |
| С Pause/Resume | 8.76с | 7с |
| Без Pause/Resume (контроль) | 8.57с | 6с |

Если бы `PauseMovieStream` реально вырезал ~3-секундный паузный интервал из записи, файл с паузой должен был получиться **короче** контрольного. На деле — ровно наоборот: файл с паузой длиннее (7с против 6с). Разница в 1 секунду хорошо объясняется обычным джиттером сетевых круговых задержек HTTP-запросов к встроенному серверу камеры (в прогоне с паузой на 2 HTTP-запроса больше) и не требует объяснения через реальный эффект паузы.

**Вывод**: `PauseMovieStream`/`ResumeMovieStream`/`StopMovieStream` принимаются HTTP-роутером камеры (в отличие от полностью неподключённых видео-сеттеров), но не оказывают измеримого эффекта ни на пассивный live-view поток, ни на активную запись видео в прошивке 3.2-int. Похоже на ещё один пример кода, физически присутствующего в прошивке (строки + обработчики + даже роутинг), но не подключённого функционально ни к чему в этой сборке — тот же паттерн, что и с видео-сеттерами, только на уровне HTTP-статуса выглядит иначе (200-без-эффекта вместо 404). Дальнейший перебор в эту сторону не выглядит перспективным без реверса самого обработчика в Ghidra (адреса `0x00155f88`-`0x00156180` в таблице) — то есть возвращаясь к статическому анализу, а не к перебору живых запросов.

## 7. Методологическая поправка (2026-07-05): "голые" команды без параметра всегда дают 404

При повторном тестировании обнаружено: **отправка команды без обязательного параметра-значения (например, `{"command":"RCISOSet"}` без `"ISO":"..."`) даёт 404 Not Found — точно так же, как несуществующая команда.** Проверено decisively в одной и той же рабочей сессии:

```
RCISOSet + ISO=Auto            -> 200
RCImageAspect + ImageAspect=4:3 -> 200
RCISOSet (без параметра)        -> 404   (та же команда, та же сессия, сразу следом)
RCImageAspect (без параметра)   -> 404
```

**Это означает, что весь предыдущий перебор из 20 вариантов имени команды для видео-сеттера (раздел 5) отправлялся "голыми" запросами и был методологически некорректен** — 404 в тех тестах мог означать не "имя команды не распознано", а просто "не хватает параметра", независимо от того, правильное ли было имя команды.

**Однако** — при повторном тесте `RCVideoFormatSet` **с параметром** (все 3 варианта ключа: `VideoFormat`, `Value`, `Mode`, значение `FHD_30` — текущее реальное значение камеры, для безопасности) — **в той же сессии, где соседние команды с параметром сработали** — всё равно 404 на все три варианта. Полный лог: [wifi-experiment-results/run_20260705_230120_bare_vs_param/log.txt](wifi-experiment-results/run_20260705_230120_bare_vs_param/log.txt).

**Вывод: результат "RCVideoFormatSet недоступен" подтверждён более строго и надёжно, чем раньше** — это не артефакт отсутствующего параметра, не проблема состояния сессии (соседние команды в той же сессии работают). Остаётся открытым: правильное ли имя параметра-ключа мы перебрали (только 3 варианта), или команда действительно не подключена к HTTP-роутеру ни под каким именем параметра.

### Побочное наблюдение: BLE-пейринг однажды не удался в Video Live View

В одной попытке BLE-пейринг завершился ошибкой `CBATTErrorDomain Code=128 "Unknown ATT error"` именно когда камера была в Video Live View; при переключении в Photo Live View пейринг сразу прошёл успешно. Не установлено, коррелирует ли это с режимом камеры или просто очередная BLE-флакиность (таких уже было несколько за сессию) — не подтверждено повторными попытками, зафиксировано как наблюдение для будущей проверки.

**Ни `RCVideoFormatSet`, ни `VideoRecordingStart`/`VideoRecordingStop`, ни `RCVASwitchSet`, `RCVAVolSet`, `RCVANoiseReduceSet`, `RCEisSwitchSet`, ни `StartMovieStream`/`StopMovieStream`/`PauseMovieStream`/`ResumeMovieStream` не встречаются нигде в приложении.** Отдельно проверено: слово "video" во всём HTTP-пакете приложения не встречается ни разу; единственные файлы с "video" в названии (`YiVideoView`, `YiVideoTitleBar`, `BaseVideoActivity`) — это виджеты **локального плеера** для просмотра уже снятых видеофайлов, никак не связанные с удалённым управлением записью.

### Вывод, закрывающий вопрос

**Официальное приложение YI Mirrorless (последняя выпущенная версия) никогда не реализовывало и не использовало ни одной команды удалённого управления видео.** Это не пробел в нашем тестировании и не путаница с именами параметров — это подтверждённый факт о реально выпущенном продукте, из первоисточника (декомпилированный APK), а не предположение. Видео-строки и обработчики, найденные в прошивке (раздел про Ghidra выше), — это код, который **не использует ни один клиент, включая официальный** — то есть либо недоделанная функциональность, зарезервированная на будущее и так и не завершённая, либо унаследованный от общей ODM-платформы Xacti код, разделяемый с другими продуктами (см. `related-projects-and-community.md`), который для YI M1 просто никогда не подключили к внешнему интерфейсу.

**Это финальный, обоснованный ответ на вопрос "почему `RCVideoFormatSet` не работает" — дальнейший поиск правильного имени параметра бессмысленен, потому что такого параметра не существует ни у одного клиента этой камеры.**

## 6. Перебор имён команды для сеттера видео-формата — отрицательный результат

Полный лог: [wifi-experiment-results/run_20260702_233800_cmdname_bruteforce/log.txt](wifi-experiment-results/run_20260702_233800_cmdname_bruteforce/log.txt).

Отправлено 20 вариантов имени команды (с `RC`-префиксом и без, с разными суффиксами: `Set`/`Select`/`Change`/`Choose`/`Switch`, по терминологии из внутренних имён прошивки `MOV_Set_WorkArea`/`ChangeSensorMode=`/`SENSOR MODE=`): `VideoFormatSet`, `RCChooseVideoFormat`, `RCSwitchVideoFormat`, `RCVideoFormat`, `VideoFormat`, `RCMovieFormatSet`, `MovieFormatSet`, `RCVideoModeSet`, `VideoModeSet`, `RCVideoResolutionSet`, `VideoResolutionSet`, `RCVideoQualitySet`, `ChangeSensorMode`, `RCSensorModeSet`, `SensorModeSet`, `RCVideoFormatSelect`, `RCVideoFormatChange`, `RCSetVideoFormat`, `SetVideoFormat`, `RCMovModeSet`.

**Результат: все 20 — 404 Not Found.** Санити-проверка в том же прогоне подтвердила, что RC-канал в это время был полностью рабочим (`GetCameraStatus` → 200 с реальными данными, `RCImageAspect` → 200) — то есть отрицательный результат не связан со сбоем соединения или сессии.

**Вывод**: смена формата/разрешения видео через HTTP Wi-Fi API в прошивке 3.2-int, по всей видимости, действительно недоступна ни под одним разумным именем команды. Учитывая, что `VideoRecordingStart`/`VideoRecordingStop` (та же таблица обработчиков в прошивке, тот же файл, те же соседние адреса, что и у `RCVideoFormatSet`, `RCVASwitchSet` и т.д. — см. `../research/yi-m1-raw-video-feasibility.md`) работают, а все "сеттеры" рядом с ними в этой же таблице — нет, наиболее вероятное объяснение: **HTTP-командный роутер этой прошивки использует отдельный список разрешённых имён команд, который не включает видео-сеттеры**, даже если сами строки и обработчики физически присутствуют в бинарнике. То есть это похоже не на "неправильно угадали имя", а на "функциональность существует в коде, но осознанно не подключена к внешнему интерфейсу в этой версии прошивки" (либо недоделанная, либо намеренно отключённая for release). Дальнейший перебор имён — низкая отдача; следующий содержательный шаг в эту сторону — не перебор строк, а дизассемблирование самой таблицы HTTP-роутера (не таблицы RC-обработчиков), чтобы увидеть точный список command-строк, которые роутер реально сверяет.

**Обновление (2026-07-06)**: гипотеза про отдельный внешний роутер-белый список проверена Ghidra-анализом полной цепочки вызовов от приёма TCP-соединения до диспетчера и **не подтвердилась** — такого списка не существует, единственная проверка имени команды во всей прошивке это уже известная таблица из 45 записей. Подробности и обоснование — `ghidra-disassembly-findings.md`, раздел "Продолжение (2026-07-06)". Вопрос закрыт.

## 9. Подтверждено: настройки (ISO/WB/цветовой стиль и т.д.) реально влияют на запись видео, а не только на фото (2026-07-06)

Вопрос пользователя: живут ли фото- и видео-режимы камеры как две изолированные подсистемы с независимыми параметрами (то есть влияют ли команды `RCISOSet`/`RCWBSet`/`RCChooseColorMode`/etc. только на фото, а на видео — нет), или это общее состояние камеры.

**Косвенная улика**: JSON-заголовок, вшитый в каждый UDP-кадр live view (см. `app/camera_session.py`, `_parse_live_metadata` — раньше эти 2048 байт просто отбрасывались перед JPEG), одновременно содержит фото-only поля (`ImageQuality`, `ImageAspect`, `FileFormat`, `Fnumber`, `DriveMode`) и видео-only поля (`VideoFormat`, `VASwitch`, `VAVol`, `VANR`, `VideoEis`) в одном общем объекте, а поля вроде `ISOSetting`/`WB`/`ColorMode`/`ShutterSpeed`/`EV`/`ExposureMode`/`MeteringMode`/`FocusMode` не раздвоены на фото- и видео-версии — одно значение на двоих. Это уже намекало на единую модель состояния, а не на два изолированных набора.

**Прямая проверка** (`yi-m1-remote-control/probe_video_param_effect.py`): `RCChooseColorMode(NaturalBW)` → `VideoRecordingStart` → 3с записи → `VideoRecordingStop` → `RCChooseColorMode(Standard)` для возврата.

**Результат: итоговое видео получилось чёрно-белым.** Однозначное прямое подтверждение — команда `RCChooseColorMode`, отправленная через тот же HTTP RC-канал, что и все "фото"-настройки, реально применяется к активной записи видео, не только к фотосъёмке.

**Вывод**: гипотеза о полностью раздельных фото/видео параметрах **не подтвердилась**. Камера использует единую модель экспозиции/цвета/etc, которая действует независимо от того, что сейчас снимается — фото или видео. Единственное, что оказалось действительно недоступно для видео через HTTP — это сам **формат/разрешение** записи (`RCVideoFormatSet` и соседи, см. выше, подтверждённый мёртвый код) — а не общие параметры экспозиции и цвета, которые работают одинаково для обоих режимов. Вопрос закрыт, дальнейшая перепроверка не требуется.

## 10. Реальные значения кропа по видео-режимам — измерено эмпирически через фотограмметрию (2026-07-07)

Статический Ghidra-анализ (`ghidra-disassembly-findings.md`, раздел "Продолжение (2026-07-06)") установил, что точные числа кропа сенсора по видео-режимам **не извлекаются из ROM** — кроп вычисляется в рантайме, статической таблицы `{режим → x,y,w,h}` в прошивке нет, а `FUN_00393d24` оказалась алгоритмом автофокуса, а не сеттером кропа. Дальнейший прогресс требовал бы динамического анализа (JTAG/дамп памяти) — то есть аппаратного вмешательства, вне software-only рамок.

Пользователь предложил обходной путь: **измерить кроп эмпирически**, сравнивая реальные снимки с зафиксированной камеры, а не разбирать прошивку.

Камера закреплена на штативе, фокус и диафрагма не менялись на всём протяжении сессии. Снята серия на одну и ту же статичную сцену (окно с жалюзи + когтеточка — сцена с чёткими горизонтальными линиями и угловатыми объектами, удобная для сопоставления):

2. Фото 3:2, 20 МП — `P7060633.JPG`, 5184×3456
3. Фото 16:9, 20 МП — `P7060634.JPG`, 5184×2920
4. Фото 1:1, 20 МП — `P7060635.JPG`, 3888×3888
5. Фото 4:3, VGA (проверка, режет ли МП-настройка поле зрения) — `P7060636.JPG`, 640×480
6. Видео FHD — `P7060637.MP4`, 1920×1080, 16:9
7. Видео "2K" — `P7060638.MP4`, 2048×1536, **4:3** (подтверждено давнее наблюдение пользователя, что "2K пишет 4:3")

## 11. Нельзя сменить видео-формат ни через `RCVideoFormatSet`, ни как параметр `VideoRecordingStart` (2026-07-07)

Гипотеза пользователя: раз отдельная команда `RCVideoFormatSet` подтверждённо мертва (404), может быть, параметр формата нужно передавать не заранее отдельной командой, а прямо вместе с `VideoRecordingStart` — то есть одной атомарной командой "начать запись в режиме X". `VideoRecordingStart` до этого тестировалась только "голой", без дополнительных полей.

**Проверено** (`probe_videorecordingstart_format.py`): камера была в режиме `4K_30` (подтверждено метаданными live view напрямую — это первое прямое наблюдение точной строки для 4K). Перебраны 6 комбинаций — три варианта названия поля (`VideoFormat`/`Value`/`Mode`, те же кандидаты, что пробовались для `RCVideoFormatSet`) × два значения (`4K_30`/`2K_30`), каждая через реальный `VideoRecordingStart` с этим полем + немедленная проверка `VideoFormat` в метаданных live view + `VideoRecordingStop`.

**Результат: ни одна комбинация не изменила отдаваемый `VideoFormat`** — во всех 6 случаях метаданные сразу после `VideoRecordingStart` показывали тот же `4K_30`, что и до теста. Косвенно подтверждено и физически: все получившиеся тестовые файлы на карте оказались в 4K (то, что было выставлено заранее на камере), не в запрошенных значениях.

**Вывод**: смена видео-формата через HTTP RC-канал недоступна ни одним из двух опробованных механизмов — ни отдельной командой, ни параметром на старте записи. В сочетании с тем, что экран камеры блокируется на всё время Wi-Fi-сессии (см. `app/ARCHITECTURE.md`, известные ограничения), это означает: **видео-режим нужно выставлять на камере до подключения и менять его нельзя никаким программным способом в рамках текущей прошивки**. Вопрос закрыт, дальнейший перебор параметров/названий полей для этой конкретной цели — низкая отдача.

## 12. Live view меняется на реальный кроп/экспозицию в момент старта записи (наблюдение пользователя, 2026-07-07)

Два связанных наблюдения из живого использования приложения (панель настроек + оверлей кропа):

1. **В момент старта записи (`VideoRecordingStart`) сам поток live view переключается с полного 4:3 превью на реальный кропнутый кадр записи.** До записи видно весь сенсорный кадр (с рамкой-подсказкой, где будет кроп); как только запись реально пошла — live view уже показывает именно ту область, что пишется на карту, один в один. То есть рамка-подсказка кропа становится избыточной/бессмысленной во время активной записи — пользователь уже смотрит прямо в кроп.

2. **Экспозиция в live view может не совпадать с реальной записью до её старта.** Пример: выставлен низкий ISO вручную — live view всё равно показывает светлую (как будто автоэкспозиция) картинку, но как только начинается запись, кадр реально темнеет до ожидаемой при этом ISO яркости. Похожая логика на первое наблюдение: **пока запись не идёт, live view выглядит как отдельный "превью"-поток с собственной (похоже, авто-) экспозицией, слабо связанный с выставленными вручную параметрами** — а в момент реальной записи используется тот же пайплайн, что и для итогового файла, с настоящей выставленной экспозицией.

**Практический вывод**: live view до нажатия записи полезен для компоновки кадра (кроме кроп-рамки, которая теперь и не нужна отдельно, раз видно сам кроп при записи), но **не является надёжным превью экспозиции при ручных настройках** — доверять яркости картинки до старта записи нельзя, только после. Как только `CameraSession.recordingStateChanged` сообщает `True` — рамки кропа скрываются (рисовать их поверх уже кропнутого кадра было бы неверно/избыточно), вместо них короткая надпись "● Recording - live view now shows the actual crop & exposure". Про несовпадение экспозиции до записи — это наблюдение задокументировано, но никакого кода/митигации под него нет (не запрашивалось, и неясно, что тут вообще чинить на нашей стороне — это, похоже, поведение самой прошивки).
